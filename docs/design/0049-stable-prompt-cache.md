# การ์ดออกแบบ 0049: ส่วนต้นของ prompt คงที่ · มีสกิลของผู้ใช้เกิน 5 ตัวแล้วไม่ช้าลง

- **สถานะ:** **อนุมัติแล้ว 2026-10-21 (Pakon)** · ทาง ข. ของการ์ด 0047 "แก้เรื่องแคชก่อน"
- **ข้อกำหนดที่อ้าง:** การ์ด 0013 (แชทในเครื่อง · อุ่นแคช) · 0018 (เลือกสกิลของผู้ใช้ 5 ตัวตามข้อความ) · 0047 (ผลรอบ 1) · ข้อเสนอความเร็ว 2026-10-01 · H4 H5 H9

## 1. ปัญหา (วัดแล้ว)

การ์ด 0047 รอบ 1 (Pi 5 · [ค่าดิบ](../benchmarks/2026-10-21-teach-local/README.md)): แอปที่ไม่มีสกิลของผู้ใช้ ถึงคำแรกมัธยฐาน **1.5 วิ** ·
มีสกิลของผู้ใช้ 9 ตัว ~**37 วิ ทุกข้อความ** · สาเหตุในโค้ด: `retrieval.pick` (การ์ด 0018) ส่งครบเมื่อมี ≤ 5 ตัว แต่เกิน 5 = เลือก 5 ตัวตามข้อความ →
รายการเครื่องมือ (อยู่ส่วนต้นของ prompt) เปลี่ยนทุกข้อความ → llama-server ใช้แคชไม่ได้ → อ่าน prompt ใหม่ (~22 token/วิ) ·
**ตอนนี้ยังไม่กระทบผู้ใช้จริง** (Pakon มี 3 ตัว) แต่การ์ด 0047/0017 ทำให้สกิลของผู้ใช้เพิ่มเรื่อย ๆ

## 2. ออกแบบที่เสนอ: ของที่คงที่ไว้ต้น · ของที่เปลี่ยนไว้ท้าย

- รายการเครื่องมือ = **คงที่ทุกข้อความ**: ask-cloud · create-skill · สกิลในตัว · **เครื่องมือเดียว `user-skill(id)`** แทนสกิลของผู้ใช้ทุกตัว
- สกิลของผู้ใช้ 5 ตัวที่ใกล้ข้อความ (ตัวเลือกเดิมของ 0018) ไปอยู่**ท้ายข้อความของผู้ใช้** ("สกิลของคุณที่อาจเกี่ยว: id — คำอธิบาย …") ·
  ส่วนที่ต้องอ่านใหม่เหลือแค่ข้อความล่าสุด + รายการสั้นนี้ (~500 token แย่สุด → ตั้งเพดานความยาว)
- AI เรียก `user-skill` ด้วย id → โค้ดตรวจว่า id อยู่ในรายการที่ให้ไปจริง (ไม่ใช่ = ไม่ทำ · H7 H8) → ทางเดิมของ handleAs
- **ขั้นแรก (ครึ่งวัน · ก่อนเขียนโค้ด):** ดู prompt ที่ chat template ของ Gemma สร้างจริง (`/apply-template` ของ llama-server บน Pi) ว่ารายการเครื่องมืออยู่ตรงไหน ·
  ถ้าแม่แบบวางเครื่องมือไว้หลังข้อความ (ไม่ใช่ปัญหาตามที่คาด) = หยุดแล้วรายงาน

ทางที่พิจารณาแล้ว: ส่งสกิลของผู้ใช้ครบทุกตัวแบบคงที่ = prompt โตไม่จำกัด (0018 วัด ~94 token/สกิล · 30 สกิลเกิน ctx 4,096) ✗ ·
แคชต่อชุดสกิล = ชุด 5 ตัวมีหลายแบบเกิน ✗

## 3. ต้นทุน

ไม่มีโมเดลใหม่ · RAM เท่าเดิม · prompt คงที่สั้นลงเล็กน้อย (สกิลของผู้ใช้ไม่อยู่ในส่วนต้น) · เวลาทำ ~1.5 วัน
