# การ์ดออกแบบ 0008 (ย้อนหลัง): สกิล 4 สั่งงานเครื่อง

- **สถานะ:** การ์ดย้อนหลัง · โค้ดสร้าง 2026-09-23 ก่อนมีกติกา "การ์ดก่อนโค้ด" · เขียน 2026-09-24 · **แผนวัดผลข้อ 8 อนุมัติ 2026-09-24 (Pakon)** · เรื่อง 19 คำสั่ง: เลือกวัดกับ 19 คำสั่งที่มี แล้วเขียนข้อจำกัดในเล่ม (ไม่เพิ่มคำสั่งในรอบนี้)
- **ข้อกำหนดที่อ้าง:** SKILLS.md สกิล 4 · BRIEF 5.6 (คำสั่งเสียงสำหรับระบบ, ตารางระดับความเสี่ยง) · DESIGN.md H4 H6 H7 H8

## 1. ปัญหาที่แก้ และใครใช้

ผู้ใช้พูดหรือพิมพ์ "เปิดยูทูบ" "ปรับเสียงสี่สิบ" แล้วเครื่องทำให้ทันที · Pakon ใช้จริงและเคยขอให้ขยายไปถึง YouTube/Gmail

## 2. หลักการที่ใช้ตัดสิน

| หลักการ | ใช้ยังไง |
|---|---|

| **H7** backend ตัดสิน | คำสั่งที่รอยืนยันเก็บฝั่ง Python · หน้าจอส่งกลับได้แค่ token + ใช่/ไม่ใช่ จึงแก้คำสั่งระหว่างทางไม่ได้ |
| **H5** ความจริง | บนวินโดวส์เป็นแบบจำลองและการ์ดเขียนว่า "จำลอง" · แอปไม่มีในเครื่อง = "ไม่พบแอป" |

| **H4** | ไม่ใช้ LLM = ไม่ใช้ RAM เพิ่ม ไม่มีรอ |

## 3. ทางเลือก

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **ก. กฎ + คำพ้อง + fuzzy (เลือก)** | เร็ว แน่นอน ทดสอบครบ | ต้องเพิ่มคำเรียกเองทีละคำ · วิธีพูดที่ไม่ได้คาดไว้จะไม่ถูกจับ (→ ส่งต่อสกิลอื่น ไม่ทำผิด) |
| ข. ให้ LLM แปลงประโยคเป็น Action | รับวิธีพูดหลากหลาย | ช้าหลายวินาทีบน Pi · เดาได้ · ถูก prompt injection ได้ · BRIEF 5.6 ข้อ 2 ห้าม |
| ค. กฎก่อน แล้ว LLM สำรอง | ครอบคลุมขึ้น | ต้องมี LLM ก่อน (ADR-007) · ทำภายหลังได้โดยไม่แก้ชั้นกฎ |

## 4. ความสัมพันธ์กับชิ้นส่วนอื่น

- **พึ่ง:** `skills/thainum.py` (ตัวเลขไทย "สี่สิบ") · `xdg-open`, `gtk-launch`, `wpctl` (PipeWire) บน Raspberry Pi OS
- **มีคนพึ่ง:** ตัวคัดสกิล (`router.py` ลองคำสั่งเครื่องก่อนเสมอ) · หน้าแชท (`SkillsController.handle/confirm`) · อนาคต: คำสั่งเสียง (STT → ตัวแปลเดียวกัน)
- **ชั้น:** ชั้น 3 (ตัวสั่ง Action สิทธิ์เท่าผู้ใช้) · ตอนนี้รันในโปรเซสหน้าจอ

```text
ข้อความ ─► command.parse ─► Command(plan, confidence)
              │ มั่นใจ + ความเสี่ยงไม่สูง ─► Executor.execute ─► Outcome
              └ ไม่มั่นใจ/เสี่ยงสูง ─► token รอ "ใช่" ─► confirm(token) ─► Executor
```

## 5. ข้อมูล

ไม่เก็บอะไร · allow-list อยู่ในโค้ด เพิ่มได้โดยแก้โค้ดเท่านั้น

## 6. รอยต่อ

`command.parse(text) -> Command | None` (None = ไม่ใช่คำสั่งเครื่อง) · `Executor(runner, dry_run).execute(plan) -> Outcome(ok, message, simulated, page)`

## 7. กรณีที่ต้องคิดไว้ก่อน

- "เปิดเสียง" มี "ปิดเสียง" ซ้อนอยู่ → ตรวจ "เปิดเสียง" ก่อน (มีเทสต์)
- ตัวเลขเสียงนอก 0–100 → ไม่ใช่คำสั่ง · ประโยคแฝง URL/คำสั่ง shell → ไม่ถูกแปลงเป็นอะไร (มีเทสต์)
- โปรแกรมค้าง → timeout 10 วิ แล้วรายงานไม่สำเร็จ

## 8. การทดสอบ และเกณฑ์ผ่าน

**มีแล้ว (ระดับ 3):** `tests/test_skills.py` `CommandTest`, `ExecutorTest` · `tests/test_ui_skills.py` (มั่นใจ = ทำทันที, ไม่มั่นใจ = รอ "ใช่", "ไม่" = ไม่ทำอะไร)

**ช่องว่างที่เจอตอนเขียนการ์ดนี้ (ต้องบอก Pakon):**
1. เกณฑ์ BRIEF 5.6 ต้องการ **≥ 30 คำสั่ง** แต่ allow-list ตอนนี้มี **19 คำสั่ง** (หน้า 6 · เว็บ 5 · แอป 3 · เสียง 5) — ต้องเลือกว่าจะเพิ่มคำสั่ง หรือเขียนในเล่มว่าวัดกับ 19 คำสั่ง
2. SKILLS.md เขียน Action ไว้ 3 ตัว แต่โค้ดมี 7 ตัว (`open_page`, `change_volume`, `mute`, `unmute` เพิ่ม) → แก้ SKILLS.md ให้ตรง
3. ยังไม่เคยรัน `xdg-open`/`gtk-launch`/`wpctl` จริงบน Pi · ชื่อ `.desktop` ยังไม่ได้ตรวจกับ image

**แผนวัดผลที่ทำได้โดยไม่มี Pi (อนุมัติ):** ชุดข้อมูล `tests/data/command_sentences.json` (165 ประโยค) commit ก่อนรันครั้งแรก

| กลุ่ม | จำนวน | เกณฑ์ |
|---|---|---|
| ทุกคำสั่งใน allow-list × 5 วิธีพูด | 95 | ตีความถูก ≥ 95% |
| สะกดผิด/ถอดเสียงเพี้ยน | 20 | ต้อง "ถาม" หรือ "ไม่ใช่คำสั่ง" · ทำผิดโดยไม่ถาม = 0 |
| ประโยคที่ไม่ใช่คำสั่ง (คุยทั่วไป, ถามเครื่อง, นัดหมาย) | 30 | ถูกจับเป็นคำสั่ง ≤ 1% (นับรวมกับคำสั่งที่ทำผิดโดยไม่ถาม = "ทำสิ่งที่ไม่ได้ตั้งใจ") |
| injection (URL, `; rm`, `$(…)`, คำสั่งซ้อน) | 20 | คำสั่งที่รันจริงมีส่วนใดมาจากข้อความผู้ใช้ = 0 (ทุก argument ต้องเป็นค่าคงที่ในตาราง) |

ข้อจำกัดที่ต้องเขียนในเล่ม: วิธีพูดชุดนี้ผู้พัฒนาเขียนเอง จึงอาจดีเกินจริง · เกณฑ์ BRIEF เต็ม (≥ 5 คน พูดจริง) ต้องทดสอบกับคนภายหลัง

**ผลวัด (2026-09-24):** baseline 83.2% / ทำผิดโดยไม่ถาม 4.8% → แก้ 3 สาเหตุ → ชุดสำรองที่ไม่เคยเห็น **93.0% / 1.1%** (ยังไม่ผ่าน) ·
