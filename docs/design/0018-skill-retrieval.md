# การ์ดออกแบบ 0018: ส่งให้ AI เฉพาะสกิลของผู้ใช้ที่เกี่ยวข้อง (top-k)

- **สถานะ:** อนุมัติ (Pakon 2026-10-01 "ทุกฟีเจอร์ดี ทำได้เลย") · สร้างแล้ว (`aipc.skills.retrieval` · SkillsController.tool_catalog) · รอวัดตามข้อ 4
- **ข้อกำหนดที่อ้าง:** การ์ด 0017 (สกิลอัตโนมัติทำให้จำนวนสกิลโตไม่จำกัด) · การ์ด 0013 (แชท · ctx 4,096)

## 1. ปัญหา (วัดแล้วบน Pi 5)

ทุกข้อความส่งรายการสกิลทั้งหมดให้ AI · สกิล 1 ตัว ≈ +94 token ≈ +4.3 วิ ตอนแคชไม่มี · ประมาณ 30 สกิล prompt เกิน 4,096 token
(ctx ของ AI) → สกิลอัตโนมัติ (0017) จะทำให้แชทพังเมื่อผู้ใช้สะสมสกิลถึงระดับนั้น ([ผลวัด](../benchmarks/2026-10-01-llm-speed-ideas-pi5/README.md) หัวข้อ 3)

## 2. ออกแบบที่เสนอ

- สกิลในตัว + ask-cloud + create-skill ส่งทุกครั้ง (ลำดับคงที่ = ส่วนต้นของ prompt คงที่ แคชบนดิสก์ใช้ได้)
- สกิลของผู้ใช้ (ที่ Claude สร้าง): ส่งเฉพาะ k ตัวที่ใกล้กับข้อความที่สุด ต่อท้ายรายการ · k = 5 (ปรับด้วยชุดพัฒนา)
- ตัวค้น: TF-IDF ของ n-gram ตัวอักษร 2–3 ตัว (ภาษาไทยไม่เว้นวรรค · ไม่ต้องมีโมเดลเพิ่ม · ไม่ใช้ RAM) บน ชื่อ + คำอธิบาย + ตัวอย่าง + คำสำคัญ
  (Tool2Vec: ตัวอย่างคำขอแทนเครื่องมือได้ดีกว่าคำอธิบาย) · ถ้ามีสกิลของผู้ใช้ ≤ k ตัว = ส่งทั้งหมด (เหมือนตอนนี้)
- กฎ "ประโยคเดิมตรงเป๊ะ" (`router.repeat_of`) ยังอยู่ก่อนถึงตัวค้น

## 3. ผลลองความเป็นไปได้ (ไม่ใช่ผลประเมิน · ชุดข้อมูลเคยใช้กับงานอื่นแล้ว)

คลัง 19 สกิล (ในตัว 5 ที่ AI เลือกได้ + Claude สร้าง 14) · ประโยค 51 ข้อ:
ค้นทั้งคลัง Recall@5 = 46/51 (90%) · 5 ข้อที่พลาดเป็นสกิลในตัวทั้งหมด → แบบที่เสนอ (สกิลในตัวส่งเสมอ) ไม่พลาดข้อเหล่านี้ ·
ค้นเฉพาะสกิลของผู้ใช้ (14 ตัว · 15 ประโยค): Recall@1 = 15/15 · เวลา ~0.2 ms/ประโยค (วินโดวส์)

## 4. การทดสอบ และเกณฑ์ผ่าน (ประกาศก่อนสร้าง)

- ชุดใหม่ที่ Claude เขียน (ไม่เห็นตัวค้น): คลังสกิลของผู้ใช้ ≥ 40 ตัว (Claude สร้างจริง ผ่านประตู 0017) + ประโยคเรียก ≥ 60 ข้อ
- Recall@5 ของสกิลของผู้ใช้ ≥ 95% · ชุดเลือกสกิล 58 ข้อบน Pi 5 ไม่ลดลงเกิน 1 ข้อ · prompt ≤ 2,000 token ที่ 40 สกิล · ค้น ≤ 20 ms บน Pi

## 5. ไม่ทำ

โมเดล embedding (กิน RAM และเวลาบน Pi · เริ่มจากแบบไม่มีโมเดลก่อน ถ้าไม่ผ่านเกณฑ์ค่อยพิจารณา)
