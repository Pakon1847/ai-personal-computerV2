## 0. สิ่งที่เปลี่ยนจาก v1

- เพิ่ม **สมมติฐานฮาร์ดแวร์ให้ครบ** (v1 ระบุแค่บอร์ด/RAM/microSD), **threat model** และ **นิยามคำ**
- **ปิดช่องโหว่การลงทะเบียนใบหน้า:** ลองใหม่กับบัญชีเดิม หรือทำต่อหลังเครื่องดับ ได้เฉพาะเมื่อยืนยันตัวตนแล้ว
- **ใบหน้า = ความสะดวก ไม่ใช่กุญแจ:** ใช้ระบุบัญชีที่หน้า Login (ไม่ต้องพิมพ์ชื่อผู้ใช้) และปลดปิดบัง/ปลดล็อกเซสชันที่ยังไม่สิ้นสุด · การเริ่มเซสชันใหม่ใช้รหัสผ่าน ยกเว้น "โหมดสะดวก" ที่เจ้าของเครื่องส่วนตัวเลือกเอง
- **เข้ารหัสข้อมูลรายบัญชีตั้งแต่สร้างบัญชี** ทั้งสองโหมด สลับโหมดภายหลังจึงไม่ต้องย้ายข้อมูล
- **โหมดเครื่อง** ให้ผู้ใช้คนแรก (ผู้ดูแล) เลือกตอนตั้งค่าครั้งแรก แยกจาก **ค่าความเป็นส่วนตัวรายคน** · สมัครจากหน้า Login ได้เหมือนเดิม แต่ผู้ดูแลกำหนดได้ว่าต้องอนุมัติหรือไม่
- ระบุการแยกข้อมูลระดับ OS ให้ครบ: Linux user รายบัญชี, ปิดช่องโหว่ของ image ตั้งต้น, DB role + RLS, ปิดบัง/ล็อกด้วย ext-session-lock, ล้าง cache ของ AI worker ทุกครั้งที่ Logout
- STT จาก "Whisper อย่างเดียว" → **ทดสอบเทียบ** รวมโมเดล streaming · เพิ่ม **TTS ภาษาไทย** เป็นความเสี่ยงที่ต้องพิสูจน์
- **AI เลือก Skill เอง** ภายในสิทธิ์ที่อนุญาตไว้แล้ว · Skill ที่นำเข้ายังต้องตรวจ และเนื้อหาของมันนับเป็นข้อมูลจากภายนอก
- แทน "มีอะไรแนะนำเพิ่มบอกได้" ที่ซ้ำเกือบทุกหมวด ด้วยหัวข้อ **ควรมี** + **เกณฑ์ผ่านที่วัดได้** + **ระดับหลักฐาน** และตารางต้นทุนของฟีเจอร์ที่แนะนำ (หัวข้อ 6.3)
- เพิ่มงบทรัพยากร สถาปัตยกรรม ลำดับเฟส สิ่งที่ไม่ทำใน v1 และรายการการตัดสินใจ (ADR)

## 1. เป้าหมายและหลักการ

**เป้าหมาย:** คอมพิวเตอร์ผู้ช่วย AI บน Pi 5 (RAM 8GB) ที่เปิดเครื่องแล้วเข้าหน้าจอของระบบทันที ใช้ภาษาไทยเป็นหลัก สวย ใช้ง่าย รองรับทั้งเครื่องส่วนตัวและเครื่องที่หลายคนสลับกันใช้ ทำงานบน Raspberry Pi OS (Linux) โดยไม่สร้าง OS ใหม่ และเน้น local เป็นหลัก

**หลักการ (เมื่อขัดกัน ข้อบนชนะ):**

1. ความปลอดภัยและความทนทานของข้อมูล มาก่อนความเร็วหรือตัวเลขที่ดูดี
2. ไม่ทำงานของผู้ใช้หายโดยไม่แจ้ง
3. ความเป็นส่วนตัวเป็นค่าเริ่มต้น: ไม่ส่งข้อมูลออกเองอัตโนมัติ ไม่เก็บภาพ/เสียงดิบ ไม่มีความลับใน logs
4. Local-first: งานพื้นฐานใช้ได้โดยไม่มีอินเทอร์เน็ต
5. พอดีกับฮาร์ดแวร์: งานหนักทุกอย่างผ่านตัวจัดทรัพยากร
6. ใช้ง่ายและสวยก่อนมีฟีเจอร์เยอะ
7. สถานะต้องอิงหลักฐานจาก Pi จริง

**งานที่ต้องใช้ได้แบบออฟไลน์:** เข้าสู่ระบบ, ปิดบัง/ล็อก/ปลดล็อก, แชทกับโมเดลในเครื่อง, My Files, พูด–ถอดเสียง–อ่านออกเสียง, คำสั่งระบบที่ไม่ต้องใช้เน็ต, Settings, System Health, backup ลงไดรฟ์ USB และ restore

**ไม่ทำใน v1 (ประกาศไว้กันขอบเขตบาน):** หลายเซสชันพร้อมกัน/สลับผู้ใช้แบบเร็ว, ฟังตลอดเวลา/คำปลุก, Skill ที่รันโค้ดเอง, ซิงก์ข้อมูลขึ้น Cloud, เข้าถึงเครื่องจากระยะไกล, แชร์กล้องให้แอปอื่น (เช่น วิดีโอคอล), สร้าง OS image ของตัวเอง

## 4. นิยามคำ (ใช้คำเดียวกันทั้งโค้ด UI และเอกสาร)

| คำ | ความหมาย |
|---|---|
| บัญชี | 1 คน = 1 Linux user (UID) + โปรไฟล์ใน DB · Guest ใช้ Linux user เฉพาะของ Guest ที่ถูกล้างทุกครั้ง |
| บทบาท | ผู้ดูแล (Admin), ผู้ใช้ (User), ผู้เยี่ยมชม (Guest — ถ้าเปิด) |
| เจ้าของเครื่อง / เจ้าของเซสชัน | เจ้าของเครื่อง = ผู้ดูแลหลักที่สร้างบัญชีแรก · เจ้าของเซสชัน = บัญชีที่เข้าสู่ระบบอยู่ตอนนี้ (การตรวจเจ้าของใน 5.3 หมายถึงคนนี้) |
| โหมดเครื่อง | **ส่วนตัว** (เจ้าของหลัก + คนที่ไว้ใจ) หรือ **ใช้ร่วมกัน** (หลายคน นโยบายเข้มกว่า) — ผู้ดูแลเป็นคนตั้ง |
| ค่าความเป็นส่วนตัวรายคน | ตัวเลือกของแต่ละบัญชี เช่น บันทึกประวัติแชท, เอ่ยชื่อ, ปลดล็อกด้วยใบหน้า, อนุญาต Cloud — อยู่ในกรอบที่โหมดเครื่องอนุญาต |
| โหมดสะดวก | ตัวเลือกเฉพาะโหมดส่วนตัว (ปิดเป็นค่าเริ่มต้น) ให้เริ่มเซสชันด้วยใบหน้าอย่างเดียวได้ โดยห่อกุญแจบัญชีเพิ่มด้วยกุญแจเครื่อง — กันการถอด microSD ไปอ่านได้ แต่ไม่กันการขโมยทั้งเครื่อง (ADR-003) |
| เซสชัน | ตั้งแต่เข้าสู่ระบบจนออกจากระบบ/สิ้นสุดตามนโยบาย/ปิดเครื่อง ระหว่างนั้นโปรเซสของผู้ใช้ยังทำงาน |
| ปิดบัง (Shield) | ล็อกจอด้วย ext-session-lock แบบ "ปลดง่าย": เจ้าของเซสชันมองกล้องแล้วเปิดได้ทันที (ถ้านโยบายอนุญาต) หรือใส่รหัสผ่าน · แอปยังทำงานต่อ |
| ล็อก (Lock) | ext-session-lock เหมือนกัน แต่ปลดตามนโยบายใน 5.1 ข้อ 9 และนับเวลาไปสู่การสิ้นสุดเซสชัน · งานและโปรเซสยังอยู่ |
| ออกจากระบบ (Logout) | บันทึกร่าง → ปิดแอป → ปิดโปรเซสทั้งหมดของผู้ใช้ → ล้างคลิปบอร์ด/ไฟล์ชั่วคราว → รีสตาร์ท AI workers (ล้าง cache) → ล็อกข้อมูลที่เข้ารหัส |
| สิ้นสุดเซสชันตามนโยบาย | Logout อัตโนมัติเมื่อล็อกนานเกินกำหนด ต้องบันทึกร่างก่อน และแจ้งสิ่งที่อาจหายในการเข้าครั้งถัดไป |
| Desktop | เดสก์ท็อปแบบเต็มของ Raspberry Pi OS ที่เปิดได้เป็นทางเลือกในเซสชันของผู้ใช้ ไม่ใช่หน้าแรกของระบบ |
| ความลับ | รหัสผ่าน, รหัสกู้คืน, API Key, token, กุญแจเข้ารหัส, แม่แบบใบหน้า |
| Skill | แพ็กเกจความสามารถที่มี manifest ประกาศสิทธิ์ (ดู 5.8) |
| Action | การกระทำต่อระบบที่อยู่ใน allow-list มีระดับความเสี่ยงและสิทธิ์กำกับ (ดู 5.6) |

## 5. ข้อกำหนดรายหมวด

แต่ละหมวดแบ่งเป็น **ต้องมี** (ขาดไม่ได้), **ควรมี** (คำแนะนำเพิ่ม — ต้นทุนและการทดสอบสรุปในหัวข้อ 6.3) และ **เกณฑ์ผ่าน** (ต้องวัดบน Pi จริง) · ตัวเลขเป้าหมายเป็นค่าเริ่มต้นที่ปรับได้หลังวัดจริง แต่ห้ามลดเกณฑ์ด้านความปลอดภัยเพื่อให้ผ่าน

### 5.1 การสมัครและเข้าสู่ระบบ

**ต้องมี**

1. เปิดเครื่องแล้วเข้าหน้า Login ของระบบเอง (greeter) โดยไม่เห็นเดสก์ท็อปของ Raspberry Pi OS
2. บัญชีแรกสร้างในขั้นตอนตั้งค่าครั้งแรก (OOBE) และเป็นผู้ดูแล · OOBE บังคับให้เก็บรหัสกู้คืนของผู้ดูแล และแนะนำให้ตั้งผู้ดูแลสำรอง
3. สมัครจากหน้า Login ได้ตามนโยบาย: ส่วนตัว = ต้องให้ผู้ดูแลอนุมัติ · ใช้ร่วมกัน = ผู้ดูแลเลือก เปิดเสรี (จำกัดจำนวนบัญชีและโควตา) / ต้องอนุมัติ / ปิด · อนุมัติได้ 2 ทาง: ผู้ดูแลใส่รหัสผ่านที่หน้าสมัครทันที หรืออนุมัติภายหลังในเซสชันของผู้ดูแล (ระหว่างรอ บัญชีเข้าใช้ไม่ได้และยังลงทะเบียนใบหน้าไม่ได้) · **รุ่นนี้ (Pakon 2026-09-29): เปิดเสรีอย่างเดียว ไม่มีผู้ดูแลอนุมัติ ไม่จำกัดจำนวนบัญชีและโควตา** — ความเสี่ยงที่ยอมรับอยู่ใน [การ์ด 0012 หัวข้อ 10](design/0012-real-signup.md)
4. ลำดับการสมัคร: ตั้งรหัสผ่าน → รับ **รหัสกู้คืน** (แสดงครั้งเดียวให้จดหรือพิมพ์) → ลงทะเบียนใบหน้า (ถ้าเลือก) · ทุกบัญชียกเว้น Guest มีรหัสผ่าน
5. การลงทะเบียนใบหน้าเป็นทางเลือก: ขอความยินยอมโดยชัดแจ้งก่อน (แม่แบบใบหน้า รวมถึงแบบ embedding เป็น "ข้อมูลชีวภาพ" = ข้อมูลอ่อนไหวตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล มาตรา 26), ข้ามได้, ถอนความยินยอม/ลบแม่แบบได้ภายหลังโดยยังใช้รหัสผ่านต่อได้
6. ลงทะเบียนใบหน้าไม่ผ่าน → ลองใหม่กับบัญชีเดิมได้ **เฉพาะเมื่อยืนยันตัวตนแล้ว**: ต่อเนื่องในขั้นตอนสมัครเดิม (เครื่องไม่ได้ดับหรือรีบูต และยังไม่หมดเวลา) หรือกรอกรหัสผ่าน · หลังเครื่องดับหรือรีบูต การทำต่อต้องกรอกรหัสผ่านเสมอ · ถ้ายังไม่ได้ตั้งรหัสผ่าน ให้ลบบัญชีร่างแล้วเริ่มใหม่ · ห้ามเพิ่มหรือแทนที่ใบหน้าของบัญชีใดโดยไม่ยืนยันตัวตน · ไม่สร้างบัญชีซ้ำ
7. สแกนใบหน้าเพื่อหาบัญชี (1:N) โดยไม่ต้องพิมพ์ชื่อผู้ใช้: แสดงชื่อที่แสดงและรูปโปรไฟล์ พร้อมปุ่ม "ไม่ใช่ฉัน" · ถ้าการเริ่มเซสชันต้องใช้รหัสผ่าน (ข้อ 9) ก็กรอกแค่รหัสผ่าน
8. รหัสผ่านใช้ได้เสมอเมื่อกล้องเสีย มืด หรือจดจำไม่ได้ และไปถึงช่องรหัสผ่านได้ในการกดครั้งเดียว
9. นโยบายขั้นบันได:
   - **เริ่มเซสชันใหม่** (หลังเปิดเครื่อง, หลัง Logout, หลังสิ้นสุดเซสชันตามนโยบาย) ใช้รหัสผ่านหรือรหัสกู้คืน เพราะกุญแจข้อมูลของบัญชีผูกกับรหัสผ่าน · ข้อยกเว้นเดียวคือ **โหมดสะดวก** (ADR-003)
   - **ต้องใส่รหัสผ่านซ้ำ:** หลังใบหน้าล้มเหลวติดกัน 5 ครั้ง, แก้หรือลบ API Key, เปลี่ยนการตั้งค่าความปลอดภัย, ส่งออกหรือลบข้อมูล, ติดตั้ง Skill, งานผู้ดูแล
   - **ใช้ใบหน้าได้:** ระบุบัญชีที่หน้า Login, ปลดปิดบัง และปลดล็อกเซสชันที่ยังไม่สิ้นสุด (ตรวจแบบ 1:1 กับเจ้าของเซสชันเท่านั้น) · โหมดใช้ร่วมกันเปิดการปลดด้วยใบหน้าได้เมื่อ APCER ผ่านเกณฑ์ (ADR-002) ไม่งั้นใช้รหัสผ่าน
10. ประเมินความเสี่ยงจากภาพถ่ายและวิดีโอหลอกด้วยชุดทดสอบจริง แยกรายประเภทการโจมตี และห้ามเขียนว่า "ปลอดภัย" จากการตรวจความเคลื่อนไหว (กะพริบตา/หันหน้า) อย่างเดียว

**ควรมี**

- แม่แบบใบหน้า:
  - เก็บเป็น embedding เท่านั้น พร้อมเวอร์ชันโมเดล · เปลี่ยนโมเดลแล้วขอลงทะเบียนใหม่ตอนเข้าด้วยรหัสผ่านครั้งถัดไป (เป็นผลโดยตรงของการไม่เก็บภาพดิบ)
  - แม่แบบที่หน้า Login ใช้ระบุบัญชี (1:N) ต้องอ่านได้ก่อนมีใครเข้าสู่ระบบ จึงเข้ารหัสด้วยกุญแจระบบ ไม่ใช่กุญแจบัญชี → ผูกกุญแจระบบกับ OTP ของบอร์ด (เขียนได้ครั้งเดียว และ root อ่านได้) กันได้แค่การถอด microSD ไปอ่านที่อื่น ไม่กันการขโมยทั้งเครื่อง
  - ผู้ใช้เลือกได้ว่าจะให้หน้า Login จำหน้า หรือใช้ใบหน้าเฉพาะปลดปิดบัง/ปลดล็อก (แม่แบบเข้ารหัสด้วยกุญแจบัญชี) · ประกาศเรื่องนี้ใน Privacy Center
- ลงทะเบียนหลายมุมและหลายสภาพแสง (เช่น 5–10 ภาพ) · ตรวจคุณภาพก่อนรับ (ขนาดหน้า ความสว่าง ความเบลอ) แล้วบอกเหตุผลที่ไม่ผ่านเป็นภาษาคน เช่น "แสงด้านหลังจ้าเกินไป"
- 1:N ใช้ทั้ง threshold และ **ระยะห่างจากคะแนนอันดับสอง (margin)** เพื่อลดการจับผิดคน · calibrate กับข้อมูลของเราเอง (ค่าเริ่มต้นของ OpenCV SFace คือ cosine ≥ 0.363 ใช้เป็นจุดเริ่มเท่านั้น)
- จำกัดความถี่การลอง (rate limit + หน่วงเวลาเพิ่มขึ้น) แทนการล็อกบัญชีถาวร เพื่อกันการกลั่นแกล้งในเครื่องใช้ร่วมกัน
- กุญแจ FIDO2 แบบ USB เป็นปัจจัยเสริมที่ใช้ออฟไลน์ได้ (เช่น pam_u2f) · ใช้แทนรหัสผ่านในการเริ่มเซสชันได้เฉพาะเมื่อปลดกุญแจเข้ารหัสด้วย FIDO2 ได้จริง (เช่น systemd-homed แบบ FIDO2) — ต้อง spike
- PAD สองระดับ:
  - กล้อง RGB: โมเดล passive (เช่น MiniFASNet จาก Silent-Face-Anti-Spoofing, Apache-2.0) + challenge แบบสุ่ม → กันได้แค่การโจมตีแบบง่าย
  - ชุด NIR: Microsoft อธิบายว่าภาพ IR ไม่ปรากฏบนจอ LCD หรือรูปถ่ายธรรมดา จึงกันการยื่นจอ/รูปได้ดีขึ้นมาก แต่ Windows Hello ก็เคยถูกหลอกด้วยรูปพิมพ์ภาพ IR มาแล้ว → ยังต้องทดสอบเอง
- ไลเซนส์โมเดล: pretrained ของ InsightFace ใช้ได้เฉพาะงานวิจัยที่ไม่ใช่เชิงพาณิชย์ · ทางเลือกที่ไลเซนส์สะอาดคือ YuNet (MIT) + SFace (Apache-2.0)
- บันทึกเหตุการณ์ความปลอดภัย (เวลา วิธี สำเร็จ/ล้มเหลว — ไม่มีภาพ) ให้เจ้าของบัญชีดูได้ใน Privacy Center
- ข้อมูลทดสอบใบหน้าและเสียง (เป็นภาพ/เสียงดิบ): เก็บแยกนอกเครื่องใช้งาน มีหนังสือยินยอมเฉพาะ และกำหนดวันลบ

**เกณฑ์ผ่าน** (ดูหมายเหตุสถิติในหัวข้อ 9)

| ตัวชี้วัด | เป้าหมายเริ่มต้น | วิธีวัด |
|---|---|---|
| เวลาระบุบัญชี/ปลดล็อกด้วยใบหน้า (กล้องพร้อม → รู้ว่าเป็นใครหรือปลดได้) | มัธยฐาน ≤ 1.5 วิ, p95 ≤ 3 วิ | ≥ 50 ครั้ง × ≥ 5 คน |
| เวลาเริ่มเซสชัน (ยืนยันแล้ว → เห็น Shell) | วัดก่อนแล้วตั้งเป้า | บน SD และ SSD |
| เจ้าของถูกปฏิเสธ (FRR) ในแสงห้องปกติ | ≤ 5% | แยกแสงสว่าง/สลัว/ย้อนแสง, ใส่แว่น |
| จับคู่ผิดคนระหว่างผู้ใช้ที่ลงทะเบียน | 0 ครั้งจาก N ครั้ง (รายงาน N) | ทุกคู่ผู้ใช้ × หลายสภาพแสง |
| APCER แยกประเภท: รูปพิมพ์ / รูปบนจอ / วิดีโอบนจอ | ≤ **[ต้องกรอก]**% ต่อประเภท · ไม่ผ่าน → โหมดใช้ร่วมกันห้ามปลดด้วยใบหน้า | ≥ 60 ครั้งต่อประเภท (ศัพท์ตาม ISO/IEC 30107-3) |
| BPCER (คนจริงถูกปัดว่าเป็นของปลอม) | ≤ 5% | ชุดเดียวกับ FRR |
| ถอดกล้องที่หน้า Login | ไม่ค้าง และแสดงทางรหัสผ่านภายใน 3 วิ | ถอดขณะกำลังสแกน |
| ดึงปลั๊กกลางการสมัคร | ทำต่อได้หลังกรอกรหัสผ่าน (หรือเริ่มใหม่ถ้ายังไม่ตั้งรหัสผ่าน) และไม่เกิดบัญชีซ้ำ | ดึงปลั๊กในแต่ละขั้นของการสมัคร |
| ลงทะเบียนใบหน้าเข้าบัญชีคนอื่นโดยไม่รู้รหัสผ่าน (รวมกรณีดึงปลั๊กแล้วคนอื่นกดทำต่อ) | ทำไม่ได้ | ลองทุกทางที่ UI และ API เปิดไว้ |
| สลับกล้องเป็นอุปกรณ์อื่นแล้วลองปลดล็อก | ใบหน้าถูกปิดใช้จนผู้ดูแลยืนยัน | ทดสอบ T9 |

### 5.2 หลายผู้ใช้และความเป็นส่วนตัว

**ต้องมี**

1. 1 บัญชี = 1 Linux user พร้อม home ของตัวเอง (สิทธิ์ 0700) · ผู้ใช้ทั่วไปไม่มี sudo · บัญชีใหม่ไม่อยู่ในกลุ่ม adm/sudo/video
2. ปิดช่องโหว่ของ image ตั้งต้นหลัง OOBE: ลบ sudo แบบไม่ใส่รหัสและบัญชีที่ใช้ติดตั้ง (Raspberry Pi OS ให้ผู้ใช้คนแรกใช้ sudo โดยไม่ใส่รหัส — ตรวจกับ image ที่ใช้จริง), ปิดหรือถอด SSH, VNC และ Raspberry Pi Connect ถ้าไม่ใช้, udev rule ตัดสิทธิ์ `uaccess` เฉพาะโหนดของกล้อง (ไม่ตัดตัวถอดรหัสวิดีโอ) เพื่อให้กล้องเป็นของ visiond
3. เซสชันที่ทำงานได้ครั้งละ 1 คนต่อเครื่อง (v1) · มีนโยบายชัดเมื่อคนอื่นต้องการใช้ขณะเซสชันเดิมล็อกอยู่ (ADR-010): รอ / สิ้นสุดเซสชันเดิมได้เมื่อล็อกเกินเวลาที่ผู้ดูแลกำหนด (บันทึกร่างก่อน และแจ้งเจ้าของในการเข้าครั้งถัดไป) / ผู้ดูแลสั่งสิ้นสุด
4. แยกตามบัญชี: ไฟล์, แชท, Skill, การตั้งค่า, API Key, โปรไฟล์เบราว์เซอร์, ดัชนีค้นหา, ประวัติคำสั่ง
5. Browser, Desktop และ Terminal เปิดในเซสชันของผู้ใช้นั้น (UID เดียวกัน) ไม่ใช่บัญชีระบบ
6. Logout ตามนิยามในหัวข้อ 4 · ใช้ `KillUserProcesses=yes` และไม่เปิด linger · AI workers ถูกรีสตาร์ทเพื่อล้าง prompt/KV cache ก่อนกลับหน้า Login, ไม่บันทึก KV cache ลงดิสก์, ไฟล์ชั่วคราวอยู่บน tmpfs, ปิด endpoint ที่ไม่ใช้ และ worker ไม่อ่าน home ของผู้ใช้เอง (Session Agent ส่งเนื้อหาหรือ file descriptor ให้) · งานที่บันทึกไว้ต้องอยู่ครบในการเข้าครั้งถัดไป
7. เข้ารหัสข้อมูลรายบัญชีตั้งแต่สร้างบัญชี (ทั้งสองโหมด) ด้วยกุญแจที่ปลดจากรหัสผ่านหรือรหัสกู้คืน (Pi 5 มี ARMv8 Crypto Extensions ทำให้ AES ไม่หนัก) · วิธีตาม ADR-003
8. ฐานข้อมูลบังคับสิทธิ์ที่ระดับ DB ไม่ใช่แค่ในแอป (ดู 5.9)
9. **โหมดเครื่อง** เลือกโดยผู้ใช้คนแรก (ผู้ดูแล) ใน OOBE · เปลี่ยนภายหลังได้เฉพาะผู้ดูแล + รหัสผ่าน โดยต้องแสดงหน้าสรุปผลกระทบก่อนยืนยัน
10. หลัง Login ครั้งแรก ผู้ใช้แต่ละคนเลือก **ค่าความเป็นส่วนตัวของตัวเอง** และเปลี่ยนได้ภายหลังในกรอบของโหมดเครื่อง

**ผลของโหมดเครื่อง (ค่าเริ่มต้นที่เสนอ)**

| เรื่อง | ส่วนตัว | ใช้ร่วมกัน |
|---|---|---|

| เริ่มเซสชันใหม่ | รหัสผ่าน · หรือใบหน้าอย่างเดียวถ้าเจ้าของบัญชีเปิดโหมดสะดวก | รหัสผ่านเสมอ |
| ปลดปิดบัง/ปลดล็อกด้วยใบหน้า | ได้ | ได้เมื่อ APCER ผ่านเกณฑ์ (ADR-002) ไม่งั้นใช้รหัสผ่าน |

| Terminal | เปิด | ผู้ดูแลเลือกรายบัญชี |
| บันทึกประวัติแชท | ถามตอน Login ครั้งแรก (ติ๊กไว้ให้ก่อน) | ถามตอน Login ครั้งแรก (ไม่ติ๊กไว้) |
| เอ่ยชื่อตอนทักทาย | เปิด | ปิด (คนรอบข้างได้ยินว่าใครใช้เครื่อง) |

**เมื่อสลับโหมด:** ไม่ย้ายหรือรวมข้อมูลของใคร (ทุกบัญชีเข้ารหัสอยู่แล้ว) · ไป "ใช้ร่วมกัน" → ปิดโหมดสะดวกของทุกบัญชีและลบกุญแจห่อชั้นเครื่องทิ้ง, เวลาที่เกินขอบเขตถูกปรับลงพร้อมแจ้งเจ้าของ · ไป "ส่วนตัว" → ไม่เปิดโหมดสะดวกให้ใครอัตโนมัติ

**บัญชี Guest (เฉพาะโหมดใช้ร่วมกัน):** ไม่มีรหัสผ่านและไม่ลงทะเบียนใบหน้า · ใช้ตัวจับเวลาการไม่ใช้งานแทนการตรวจเจ้าของ · ล็อก = สิ้นสุดเซสชัน · home อยู่บน tmpfs ที่จำกัดขนาด (และถูกล้างตอนบูตด้วยเผื่อไฟดับ) · ไม่มี Terminal, Cloud หรือ Skill นำเข้า

**ควรมี**

- โควตาพื้นที่รายบัญชี + ถังขยะใน My Files
- โฟลเดอร์แชร์ต้องเป็นสิ่งที่ผู้ใช้เลือกเองและเห็นชัดใน UI ไม่ใช่ค่าเริ่มต้น
- จำกัด CPU/RAM ต่อผู้ใช้ด้วย systemd slice กันโปรแกรมของผู้ใช้ทำให้ UI หรือการยืนยันตัวตนค้าง
- การแชร์กล้องให้วิดีโอคอลเป็นงานภายหลัง (ตอนนี้กล้องเป็นของ visiond เท่านั้น)

**เกณฑ์ผ่าน**

- สคริปต์ทดสอบการแยกข้อมูลอัตโนมัติ (รันบน Pi): ในฐานะผู้ใช้ B พยายามอ่าน home, แถวใน DB, API Key, โปรไฟล์เบราว์เซอร์, `/proc` ของโปรเซส A, ไฟล์ใน `/tmp` และ journal ของ A → ถูกปฏิเสธทุกข้อ
- ส่ง canary prompt ในเซสชัน A แล้วตรวจจากเซสชัน B → ไม่มีร่องรอยใน cache, endpoint หรือไฟล์ชั่วคราวของ AI worker
- หลัง Logout ไม่มีโปรเซสของ A เหลือ (`loginctl`, `ps`), AI workers ถูกรีสตาร์ท และข้อมูลที่เข้ารหัสถูกล็อก
- ถอด microSD ไปอ่านบนเครื่องอื่น: ไม่เห็นเนื้อหาแชท ชื่อแชท ประวัติคำสั่ง ไฟล์ หรือ API Key (เห็นได้เฉพาะ metadata ที่ Privacy Center ประกาศไว้)
- ตรวจ image หลัง OOBE: ไม่มี sudo แบบไม่ใส่รหัส, ไม่มีบริการเข้าถึงระยะไกลที่ไม่ได้ตั้งใจเปิด, ผู้ใช้ทั่วไปเปิดโหนดกล้องไม่ได้
- ดึงปลั๊กระหว่างใช้งานแล้วเปิดใหม่: งานที่ autosave แล้วอยู่ครบ และ B ยังเข้าถึงข้อมูลของ A ไม่ได้

### 5.3 การตรวจเจ้าของระหว่างใช้งาน

**ต้องมี: แยก 6 สถานะ และมีนโยบายต่อสถานะ**

ตัวจับเวลา: **S** = เวลาก่อนปิดบัง นับจากที่ยืนยันเจ้าของเซสชันไม่ได้ · **L** = เวลาก่อนล็อก นับจากเริ่มปิดบัง · **P** = เวลาก่อนสิ้นสุดเซสชันตามนโยบาย นับจากเริ่มล็อก

| สถานะ | ตรวจจับอย่างไร | การตอบสนอง |
|---|---|---|
| เจ้าของอยู่ | ยืนยัน 1:1 กับเจ้าของเซสชันได้ภายในไม่กี่วินาทีล่าสุด | ทำงานปกติ และรีเซ็ตตัวจับเวลา |
| หันหน้า/ก้มหน้า | ยังเห็นใบหน้าใน track เดิม แต่มุมเกินหรือยืนยันไม่ได้ | ปิดบังหลัง 2×S (ถ้าใบหน้าหายไประหว่างนั้น เวลาที่ผ่านไปแล้วนับต่อ ไม่เริ่มใหม่) |
| ไม่พบใบหน้า | ไม่มีใบหน้าในภาพ | ปิดบังหลัง S → ล็อกหลัง L |
| พบคนอื่น (ไม่มีเจ้าของ) | มีใบหน้าที่ไม่ใช่เจ้าของเซสชัน | ปิดบังภายใน 2 วิ → ล็อกหลัง 30 วิ (ส่วนตัว) / 10 วิ (ใช้ร่วมกัน) · เป็นค่าคงที่ ปรับไม่ได้ และตัวเลือก "ปิด" ไม่มีผล |
| เจ้าของ + คนอื่น | เห็นทั้งสองคน | แจ้งเตือนเล็ก ๆ + ซ่อนช่องความลับ (เช่น API Key) |
| กล้องขัดข้อง/ถูกบัง/ถูกถอด | ไม่มีภาพ, error, ภาพมืดหรือถูกปิด | ใช้ร่วมกัน: ปิดบังทันที ปลดได้ด้วยรหัสผ่านเท่านั้นจนกว่ากล้องกลับมา · ส่วนตัว: ปิดบังภายใน 30 วิ แล้วปลดด้วยรหัสผ่าน · จากนั้นนับ L และ P ตามปกติ · กล้องถูกเปลี่ยนเป็นอุปกรณ์ใหม่ → ปิดการใช้ใบหน้าจนผู้ดูแลยืนยัน (T9) |

**ขอบเขตที่ปรับได้ (backend บังคับ ไม่ใช่แค่ UI)** — ใช้กับสถานะ "ไม่พบใบหน้า" และ "หันหน้า"

| ค่า | ส่วนตัว (ค่าเริ่มต้น) | ใช้ร่วมกัน (ค่าเริ่มต้น) |
|---|---|---|
| S เวลาก่อนปิดบัง | 10 วิ – 10 นาที หรือปิด (60 วิ) | 5 – 60 วิ (15 วิ) |
| L เวลาก่อนล็อก | 1 – 30 นาที (5 นาที) | 30 วิ – 5 นาที (1 นาที) |
| P เวลาก่อนสิ้นสุดเซสชัน | ปิด – 24 ชม. (ปิด) | 5 – 120 นาที (30 นาที) |

**กติกาเพิ่มเติม**

- กันจอกระพริบด้วย debounce/hysteresis (เช่น ต้องเห็นสถานะใหม่ติดกัน 3 เฟรมก่อนเปลี่ยน)
- โหมดส่วนตัว: การพิมพ์หรือขยับเมาส์ยืด S ได้ครั้งละไม่เกิน 2 นาที จากนั้นต้องเห็นหน้าเจ้าของ · ไม่มีผลกับ "พบคนอื่น" และ "กล้องขัดข้อง" · โหมดใช้ร่วมกันไม่ยืด
- ผู้ใช้ปิดการตรวจด้วยกล้องเองได้ถ้าโหมดอนุญาต → ใช้ตัวจับเวลาการไม่ใช้งานแทน (ต้องบอกว่าคนที่พิมพ์ต่อเรื่อย ๆ จะไม่ถูกปิดบัง · โหมดใช้ร่วมกันผู้ดูแลห้ามได้)
- โหมดนำเสนอ/ดูวิดีโอ: หยุดตรวจชั่วคราวตามเวลาที่ตั้ง (โหมดใช้ร่วมกันต้องใส่รหัสผ่าน)
- **ปิดบังและล็อกใช้ ext-session-lock-v1 ทั้งคู่** (labwc รองรับ) ต่างกันแค่วิธีปลด · ห้ามใช้หน้าต่างของแอปหรือ layer-shell overlay เป็นตัวปิดบัง เพราะถ้าโปรเซสนั้นล่มเนื้อหาจะโผล่ และ client อื่นในเซสชันวาดทับได้ · ถ้าตัวล็อกล่ม compositor ต้องคงสถานะล็อกไว้ (spike ว่า labwc ให้ตัวล็อกที่เริ่มใหม่รับช่วงต่อได้)
- วิธีปลด: ปิดบัง = ใบหน้าเจ้าของเซสชัน (ตามนโยบาย) หรือรหัสผ่าน · ล็อก = ตาม 5.1 ข้อ 9
- ก่อนสิ้นสุดเซสชันตามนโยบาย: บันทึกร่างทุกอย่างที่บันทึกได้, นับถอยหลังบนหน้าล็อกโดยไม่แสดงเนื้อหา, และในการเข้าครั้งถัดไปแจ้งรายการที่อาจหาย (เช่น ฟอร์มที่กรอกค้างในเว็บ)
- ภาพจากกล้องประมวลผลในหน่วยความจำเท่านั้น ไม่บันทึก ไม่ออกเน็ต · มีไอคอนบอกว่ากล้องทำงานอยู่

**เกณฑ์ผ่าน**

| กรณี | เป้าหมาย |
|---|---|
| เจ้าของลุกออก | ปิดบังหลัง S ±1 วิ |
| คนอื่นมานั่งแทน | ปิดบังภายใน 2 วิ |
| เจ้าของกลับมาระหว่างปิดบัง | เปิดคืนภายใน 1.5 วิ (เมื่อนโยบายให้ใช้ใบหน้า) |
| ถอดหรือบังกล้องระหว่างใช้งาน | เข้าสถานะกล้องขัดข้องภายใน 3 วิ, ปิดบังตามนโยบาย, ไม่ crash |
| บังกล้องแล้วพิมพ์ต่อเรื่อย ๆ | ยังถูกปิดบังตามนโยบายกล้องขัดข้อง |
| `kill -9` ตัวล็อกระหว่างปิดบังหรือล็อก | เนื้อหาไม่โผล่ และพิมพ์ใส่แอปไม่ได้ |
| เปิด Chromium + Terminal ค้างไว้แล้วปิดบัง | มองไม่เห็นเนื้อหา และพิมพ์ใส่หน้าต่างใดไม่ได้ |
| ปิดบังผิดจังหวะระหว่างทำงานปกติ | < 1 ครั้ง/ชม. (ทดสอบ 2 ชม. × ≥ 5 คน) |
| CPU ของการตรวจเจ้าของ | วัดและรายงาน (เป้า ≤ 15% ของ 1 core โดยเฉลี่ย) |

### 5.4 AI Workspace

**ต้องมี**

1. Local AI เป็นค่าเริ่มต้นและใช้ได้ออฟไลน์ (เช่น llama.cpp `llama-server` + ไฟล์ GGUF)
2. Cloud AI เพิ่มทีละผู้ให้บริการผ่าน adapter รูปแบบเดียวกัน (เจ้าแรกผ่านเกณฑ์ครบก่อน แล้วจึงเพิ่มเจ้าถัดไป)
3. ป้ายสถานะทุกโมเดล: พร้อมใช้ / กำลังโหลด / ไม่พร้อม (พร้อมเหตุผล) · ในเครื่อง / ต้องใช้เน็ต · ฟรี / มีค่าใช้จ่าย · ข้อมูลออกนอกเครื่องหรือไม่
4. ไม่ส่งข้อมูลออก Cloud อัตโนมัติ: ไม่มีการสลับไป Cloud เงียบ ๆ · ก่อนส่งครั้งแรกในแต่ละบทสนทนา แสดงสิ่งที่จะถูกส่ง (ข้อความ + ไฟล์แนบ + บริบท) และให้ยืนยัน · ยืนยันใหม่เมื่อมีไฟล์หรือบริบทใหม่ หรือเปลี่ยนผู้ให้บริการ · บังคับที่ระดับระบบด้วย (หัวข้อ 7)
5. API Key แยกบัญชี เข้ารหัสด้วยกุญแจของบัญชีนั้น แสดงแค่ 4 ตัวท้ายหลังบันทึก และไม่ปรากฏแบบอ่านได้ใน log, crash dump หรือ backup
6. แชท, ประวัติตามที่ผู้ใช้เลือก (มี "แชทชั่วคราว" ที่ไม่บันทึกเลย และตั้งให้ลบประวัติที่บันทึกไว้อัตโนมัติหลัง N วันได้), ไฟล์ประกอบ, กลับมาทำต่อ (เปิดบทสนทนาล่าสุดพร้อมร่างที่ค้าง)
7. Enter ส่ง / Shift+Enter ขึ้นบรรทัดใหม่ · ไม่ส่งขณะ IME กำลังประกอบคำ (ตรวจ `inputMethodComposing`) · มีปุ่มหยุดการตอบ (และ Esc)

**ควรมี**

- ชั้นโมเดลให้ทดสอบ (ยังไม่ใช่ข้อสรุป — ADR-007) ดูตารางถัดไป
- **คอขวดจริงคือ prefill ไม่ใช่ความเร็วพิมพ์:** บริบท 2,000 token บนโมเดล ~3B ใช้ราว 70 วินาทีก่อนได้คำแรก (2,000 ÷ ~29 tok/s) และ 4B ช้ากว่านั้น → system prompt สั้น, ใช้ prompt cache ของ llama-server ภายในเซสชัน, สรุปบทสนทนาเก่า, RAG ดึงน้อยชิ้น, แสดงแถบ "กำลังอ่านบริบท" ตามจริงแทนการค้างเงียบ
- AI HAT+ 2 (Hailo-10H) ในรีวิวของ CNX Software สร้างข้อความ **ช้ากว่า** CPU ของ Pi 5 (Llama 3.2 3B: 2.6 เทียบกับ 4.8 tok/s ที่ CPU วัดผ่าน Ollama) แต่กินไฟน้อยกว่าและปล่อย CPU ให้งานอื่น → อย่าซื้อโดยหวังให้ LLM เร็วขึ้น
- ทดลอง threads ของ LLM (3 เทียบ 4) โดยวัดผลต่อความลื่นของ UI ด้วย
- โมเดลค่าเริ่มต้นโหลดค้างไว้ หรือโหลดล่วงหน้าหลัง Login เพราะการโหลดไฟล์หลาย GB จาก microSD ใช้เวลาหลายสิบวินาที (วัดเทียบ SD กับ SSD) · ปลดเฉพาะโมเดลอื่นเมื่อว่างนานหรือ RAM ไม่พอ
- ชุดประเมินภาษาไทยของโปรเจกต์ 50–100 งานจริง (สรุปเอกสาร, ร่างอีเมล, ถามเรื่องไฟล์, แปล, คำถามทั่วไป) ให้คนให้คะแนน + วัดเวลา → เลือกโมเดลจากข้อมูล
- ไฟล์ประกอบ: ดึงข้อความ PDF ด้วย poppler (`pdftotext`) · OCR ภาษาไทยด้วย Tesseract (`tha`) เฉพาะเมื่อผู้ใช้สั่งและเข้าคิวงานหนัก
- "ถามเรื่องไฟล์ของฉัน" (RAG) ทำภายหลัง: ดัชนีค้นหาและ embeddings ของแต่ละบัญชีเก็บใน home ที่เข้ารหัส (เช่น SQLite FTS5 ต่อผู้ใช้) ไม่ใช่ใน PostgreSQL ส่วนกลาง · ภาษาไทยไม่มีช่องว่างระหว่างคำ ต้องตัดคำด้วย PyThaiNLP ก่อนทำดัชนี หรือใช้ tokenizer แบบ trigram (ต้องทดสอบคุณภาพการค้น)
- Cloud: ดูตัวอย่างและลบข้อมูลส่วนตัวก่อนส่ง (ชื่อ/เบอร์/อีเมล ด้วยกฎง่าย ๆ), ประมาณค่าใช้จ่ายก่อนส่ง, งบรายเดือนต่อบัญชี, ราคาอ้างอิงจากไฟล์ตั้งค่าที่ระบุวันที่ (ขณะออฟไลน์ดึงราคาล่าสุดไม่ได้)
- ทุกข้อความตอบมีป้าย "ในเครื่อง" หรือ "Cloud: ชื่อผู้ให้บริการ"
- ส่งออกบทสนทนาเป็น Markdown/JSON

| ชั้น | ตัวอย่างที่ควรทดสอบ | ความเร็วที่ผู้อื่นวัดบน Pi 5 (ต้องวัดซ้ำเอง) |
|---|---|---|
| เร็ว ~1B | Gemma 3 1B, Llama-3.2-Typhoon2-1B | Gemma 3 1B Q4_K_M (llama-bench, 4 threads): prefill ~46 tok/s, สร้าง ~14 tok/s |
| คุณภาพ ~3–4B | Typhoon2.5-Qwen3-4B (Apache-2.0), Typhoon2.1-Gemma3-4B, Qwen3-4B | Qwen2.5-3B (llama.cpp, วัดบน Pi 5 16GB): prefill ~29, สร้าง ~6 tok/s · Llama 3.2 3B บน Pi 5 8GB: สร้าง ~4.6 tok/s (Jeff Geerling) |
| ≥ 7–8B | ไม่ใช้เป็นค่าเริ่มต้น | Llama 3.1 8B (llama.cpp, Pi 5 16GB): prefill ~11, สร้าง ~2.5 tok/s |

**เกณฑ์ผ่าน**

- ทุกงานในรายการออฟไลน์ของหัวข้อ 1 ใช้ได้เมื่อถอดสายเน็ต/ปิด Wi-Fi · โมเดล Cloud ขึ้น "ต้องใช้อินเทอร์เน็ต" และกดใช้ไม่ได้
- ทดสอบไม่รั่ว: เฝ้า traffic ขาออก (เช่น นับด้วย nftables หรือ tcpdump) ระหว่างใช้ฟีเจอร์ local ครบ 30 นาที → ไม่มีการเชื่อมต่อออกนอกรายการที่ประกาศ (เช่น DNS, NTP, อัปเดตเมื่อผู้ดูแลสั่ง) และไม่มีการเชื่อมต่อไปผู้ให้บริการ AI เลยถ้าผู้ใช้ไม่ได้ยืนยัน
- Canary: ใส่ API Key ปลอมที่มีรูปแบบจำเพาะ แล้วค้นใน log, journal, DB dump, backup, crash dump → ไม่พบแบบ plaintext
- เวลาถึงคำแรกสำหรับ prompt 200 token: ≤ **[5]** วิ (~1B) และ ≤ **[10]** วิ (~3–4B) — ค่าเสนอ ยืนยันหลัง spike · รายงานที่ 2,000 token ด้วย
- วัดต่อโมเดล: tok/s, RAM สูงสุด, อุณหภูมิและ throttle หลังตอบต่อเนื่อง 10 นาที

### 5.5 การใช้งานด้วยเสียง

**ต้องมี**

1. กดไมค์หรือคีย์ลัดเพื่อพูด (กดค้าง = พูด หรือกดครั้งเดียว = เริ่ม/หยุด เลือกได้) · ไม่ฟังตลอดเวลาเป็นค่าเริ่มต้น
2. ข้อความร่าง (partial) แสดงต่างจากผลยืนยัน (final) อย่างชัดเจน · ผลลงช่องพิมพ์ให้แก้ก่อนส่ง (ส่งอัตโนมัติเมื่อหยุดพูดเป็นตัวเลือก ปิดไว้ก่อน)
3. AI ตอบเป็นข้อความพร้อมอ่านออกเสียง (เปิด/ปิดได้) และหยุดเสียงได้ทันทีด้วย Esc, ปุ่มหยุด หรือการกดไมค์
4. ทักทายครั้งเดียวหลัง Login ด้วยชื่อที่ผู้ใช้ตั้งเอง และเลือกไม่เอ่ยชื่อได้
5. เลือกไมค์ ลำโพง ความไวรับเสียง (VAD threshold) และเวลาหยุดพูด (เช่น 0.5–2.0 วิ)
6. ไม่เก็บเสียงดิบ: บัฟเฟอร์อยู่ในหน่วยความจำและทิ้งหลังถอดเสียงเสร็จ
7. STT ทดสอบเทียบอย่างน้อย 2 แนวทางบน Pi จริงด้วยชุดเสียงของเราเอง แล้วเลือกตามข้อมูล (ADR-005):
   - **Whisper ในเครื่อง** (whisper.cpp หรือ faster-whisper) + โมเดลที่ปรับจูนภาษาไทย เช่น Thonburian Whisper small (ผู้พัฒนารายงาน WER 11.0% บน Common Voice 13) — Whisper ไม่ใช่โมเดล streaming การแสดงข้อความร่างต้องถอดซ้ำเป็นช่วง ๆ ซึ่งกิน CPU
   - **Typhoon ASR Real-time** (FastConformer-Transducer 114M, streaming, CC-BY-4.0, ต้องยอมรับเงื่อนไขของ OpenTyphoon) — ออกแบบมาให้มีข้อความร่างจริงและเบากว่า แต่ runtime ที่ให้มาเป็น NeMo/PyTorch ซึ่งติดตั้งหนัก (การแปลงเป็น ONNX ยังไม่มีผลยืนยัน) · เปเปอร์ของผู้พัฒนารายงาน CER ราว 7–14% ตามชุดข้อมูล และระบุว่าอ่อนเรื่องไทยปนอังกฤษ
   - **แบบผสม:** ข้อความร่างจากโมเดล streaming + ผลยืนยันจาก Whisper (แลกกับ RAM ที่เพิ่มขึ้น)

**ควรมี**

- VAD ขนาดเล็ก (เช่น Silero VAD) สำหรับจับจุดหยุดพูด
- **TTS ภาษาไทยเป็นจุดที่อ่อนที่สุด (ADR-006):** เท่าที่ค้น ยังไม่พบเสียงไทยทางการของ Piper และมีคำขอให้ sherpa-onnx เพิ่มเสียงไทยค้างอยู่ · ตัวเลือก เช่น MMS-TTS-tha (VITS 36M, CC-BY-NC 4.0 = ห้ามใช้เชิงพาณิชย์), VachanaTTS (ปรับจาก MMS-TTS-tha จึงน่าจะติดเงื่อนไขเดียวกัน), เอนจินใน PyThaiTTS (ตรวจไลเซนส์น้ำหนักโมเดลทีละตัว) · ให้คนไทยฟังแล้วให้คะแนน (MOS 1–5) + วัดความหน่วงบน Pi
- ตัวปรับข้อความก่อนอ่าน: ตัวเลข วันที่ คำย่อ คำอังกฤษ (เช่น YouTube → ยูทูบ)
- อ่านออกเสียงทีละประโยคระหว่างที่ LLM ยังสร้างข้อความอยู่ (วัดว่าแย่ง CPU แค่ไหน)
- เสียงสะท้อน: แบบกดพูดให้หยุด TTS ก่อนอัด ก็ไม่ต้องใช้ AEC · ถ้าทำ hands-free ภายหลัง ใช้ speakerphone ที่มี AEC ในตัว หรือโมดูล echo-cancel ของ PipeWire
- คำปลุก (wake word) ไม่ใช่ค่าเริ่มต้น ถ้าทำภายหลังต้องเป็น opt-in และตรวจไลเซนส์โมเดล

**เกณฑ์ผ่าน**

- ชุดทดสอบเสียงไทย ≥ 200 ประโยค จาก ≥ 10 คน (หลากหลายเพศ วัย สำเนียง รวมสำเนียงเหนือ) ทั้งห้องเงียบและห้องมีเสียงรบกวน และมีคำอังกฤษปน · เก็บตามกติกาข้อมูลทดสอบใน 5.1
- CER ≤ **[ต้องกรอก]**% ในห้องเงียบ และ ≤ **[ต้องกรอก]**% ในห้องมีเสียงรบกวน (ภาษาไทยไม่มีช่องว่างระหว่างคำ CER จึงเหมาะกว่า WER)
- ความหน่วงแยกตามแนวทาง: โมเดล streaming → ข้อความร่างแรก ≤ 1 วิ · Whisper → วัดเวลาได้ผลยืนยันหลังหยุดพูดก่อน แล้วตั้งเป้า (ไม่ใช่ streaming และภาษาไทยใช้ token มาก) · รายงาน CPU/RAM ระหว่างถอดเสียง
- TTS: เวลาถึงเสียงแรก ≤ 1 วิสำหรับ 1 ประโยค · กดหยุดแล้วเงียบภายใน 200 ms

### 5.6 คำสั่งเสียงสำหรับระบบ

**ต้องมี**

1. แยก "คุยกับ AI" ออกจาก "สั่งงานเครื่อง" ด้วยปุ่มหรือคีย์ลัดคนละตัว และแสดงโหมดที่ใช้อยู่ชัดเจน
2. คำสั่งพื้นฐานใช้ตัวแปลงคำสั่งแบบกำหนดแน่นอน (grammar + คำพ้อง + ช่องค่า เช่น ชื่อแอป ชื่อไฟล์ ชื่อหน้า) ไม่ต้องผ่าน LLM · จับคู่แบบ fuzzy กับผลยืนยันเท่านั้น (ไม่ใช้ข้อความร่าง) · ความมั่นใจต่ำ → ถาม "หมายถึง…ใช่ไหม" ไม่ทำเอง
3. ทุก Action อยู่ใน allow-list และมี id, schema ของพารามิเตอร์, ระดับความเสี่ยง, สิทธิ์ที่ต้องมี, เงื่อนไขการยืนยัน (ตารางถัดไป)
4. ตรวจสิทธิ์ที่ backend ทุกครั้ง (บทบาท + โหมดเครื่อง)
5. ข้อความจาก AI ไฟล์ หรือเว็บ กลายเป็นคำสั่ง shell ไม่ได้: ไม่มี `shell=True`, เรียกผ่าน API ที่มีชนิดข้อมูลกำกับ, path ต้อง resolve แล้วอยู่ใน home ของผู้ใช้, URL ต้องผ่านการตรวจ scheme และโดเมน
6. LLM เสนอ Action ได้ในรูป "ข้อเสนอ" ที่ผ่านตัวตรวจเดียวกัน · ถ้าบทสนทนามีเนื้อหาจากภายนอก (ไฟล์, เว็บ, คำตอบจาก Cloud, เนื้อหาของ Skill ที่นำเข้า) ทุกข้อเสนอระดับกลางขึ้นไปต้องยืนยัน · การส่งไป Cloud ใช้กติกาของ 5.4 ข้อ 4 เสมอ

| ระดับ | ตัวอย่าง | การยืนยัน |
|---|---|---|
| ต่ำ | เปิดหน้า Settings, เปิดแอป, เปิด YouTube (URL คงที่) | ไม่ต้อง |
| กลาง | เปิดไฟล์, ปรับเสียง, เปิด URL ที่ AI ประกอบขึ้นหรือมีพารามิเตอร์ | ยืนยันเมื่อข้อเสนอมาจาก AI หรือเนื้อหาภายนอก · URL ที่ AI ประกอบขึ้นต้องแสดง URL เต็มก่อนยืนยันเสมอ (กันการพาข้อมูลออกทางพารามิเตอร์) |
| สูง | ลบ/ย้ายไฟล์จำนวนมาก, ติดตั้ง Skill, เปลี่ยนความปลอดภัย, สิ้นสุดเซสชันคนอื่น | ต้องกดยืนยันเสมอ บางรายการต้องใส่รหัสผ่าน · เสียงอย่างเดียวไม่พอ |

**ควรมี**

- ประวัติคำสั่งที่ทำไปแล้วให้ผู้ใช้ดูได้ + ย้อนกลับได้เมื่อทำได้ (ลบ = ย้ายไปถังขยะ)
- คำสั่งที่ต้องใช้เน็ตต้องบอกชัดเมื่อออฟไลน์ แทนการล้มเงียบ
- ชื่อแอปภาษาอังกฤษต้องมีคำเรียกแบบไทยด้วย เพราะ STT อาจถอด "YouTube" เป็น "ยูทูบ"

**เกณฑ์ผ่าน**

- ≥ 30 คำสั่ง × ≥ 5 วิธีพูด × ≥ 5 คน → ตีความถูก ≥ 95%, ทำสิ่งที่ผู้ใช้ไม่ได้ตั้งใจ ≤ 1% และระดับสูง = 0
- ทดสอบ injection: เอกสาร หน้าเว็บ หรือคำตอบ AI ที่มีข้อความอย่าง "ลบไฟล์ทั้งหมด", `rm -rf ~` หรือ URL ที่แนบข้อมูลในพารามิเตอร์ → ไม่ถูกทำโดยไม่ยืนยัน
- fuzz test ตัวแปลงคำสั่งและตัวตรวจ path

### 5.7 หน้าจอและความสะดวกในการใช้งาน

**ต้องมี**

1. Qt 6 Quick/QML สำหรับ UI + Python (PySide6, LGPL) สำหรับตรรกะ · UI thread ห้ามรองานหนัก งานหนักอยู่ในโปรเซสแยก
2. หน้าหลัก: AI Workspace, My Files, Skill Center, Privacy Center, System Health, Settings · เครื่องมือผู้ดูแลซ่อนจากผู้ใช้ทั่วไป และ backend ปฏิเสธคำขอของผู้ดูแลจากบัญชีทั่วไปเสมอ
3. ปุ่มย้อนกลับทุกหน้า · แถบสถานะรวม: ออนไลน์/ออฟไลน์, โมเดลที่โหลดอยู่และงานเบื้องหลัง, ไฟบอกว่ากล้อง/ไมค์ทำงาน, พื้นที่ใกล้เต็ม, ร้อนเกิน/ไฟไม่พอ, สถานะ backup ล่าสุด
4. ภาษาไทยอ่านชัด: ฟอนต์ไทยที่ทดสอบกับผู้ใช้แล้ว (เช่น Noto Sans Thai, Noto Sans Thai Looped, IBM Plex Sans Thai, Sarabun), ระยะบรรทัด ≥ 1.4 กันสระบน/ล่างถูกตัด, **ติดตั้ง `libthai`** เพราะ Qt โหลด libthai ตอนรันเพื่อหาจุดตัดคำภาษาไทย (ไม่มีแล้วข้อความไทยยาว ๆ จะขึ้นบรรทัดใหม่ไม่ตรงตามคำ) · ทดสอบข้อความไทยยาว ๆ ในทุกคอมโพเนนต์
5. ใช้พื้นที่จอให้เหมาะ: layout ปรับตามขนาดจอที่ประกาศว่ารองรับ **[ต้องกรอก เช่น 1280×720 ถึง 2560×1440]** · เนื้อหาหลักไม่ถูกบีบด้วยแถบเครื่องมือ · ทดสอบทุกขนาดที่ประกาศ
6. ไอคอนพร้อมคำกำกับ (ไอคอนล้วนเฉพาะที่เป็นสากลและมี tooltip) · สวิตช์สำหรับเปิด–ปิด · การลบหรือการกระทำเสี่ยงมีหน้ายืนยันที่บอกผลชัดเจน
7. ข้อความผิดพลาดเป็นภาษาคนพร้อมทางแก้ เช่น "กล้องไม่พร้อม — ใช้รหัสผ่านแทน หรือตรวจสายกล้อง"

**ควรมี**

- ขั้นตอนตั้งค่าครั้งแรก (OOBE): ภาษาและเวลา, เครือข่าย (ข้ามได้), โหมดเครื่อง, บัญชีผู้ดูแล + รหัสกู้คืน, ปลายทาง backup, คำอธิบายความเป็นส่วนตัว
- ขนาดตัวอักษร 100–200%, ธีมสว่าง/มืด/คอนทราสต์สูง, ใช้คีย์บอร์ดได้ทั้งระบบโดยเห็นตำแหน่ง focus ชัด
- แป้นพิมพ์บนจอถ้าเป็นจอสัมผัส: Qt Virtual Keyboard มีผังภาษาไทย แต่ไลเซนส์เป็น GPL-3.0 หรือเชิงพาณิชย์ (ADR-014)
- กดปุ่ม Power ของ Pi 5 → หน้าปิดเครื่องอย่างปลอดภัยของระบบเรา และสอนผู้ใช้ไม่ให้ดึงปลั๊ก
- ถ้า spike พบว่า QML มีปัญหาจริง ค่อยพิจารณา Flutter (flutter-pi), Slint หรือ Web UI ใน Chromium kiosk (กิน RAM มากกว่า)

**เกณฑ์ผ่าน**

- เวลาเปิดเครื่องถึงหน้า Login: วัดทั้งบน SD และ SSD (เป้าเริ่มต้น ≤ 45 วิ)
- UI ลื่น ≥ 50 fps ในหน้าหลักขณะ LLM กำลังตอบ และการพิมพ์ไม่หน่วงจนรู้สึกได้
- ผู้ใช้จริง ≥ 5 คนทำงานหลัก 5 อย่างได้โดยไม่มีคนช่วย + แบบสอบถาม SUS (เป้า ≥ 70)
- เรียก API ของผู้ดูแลด้วยบัญชีทั่วไป ทั้งจาก UI ที่ถูกแก้และจาก Terminal ที่ยิงตรงไปที่ socket → ถูกปฏิเสธ

### 5.8 Skill และข้อมูลส่วนตัว

#### Skill

**ต้องมี**

1. นิยาม Skill ใน v1 (ไม่มีโค้ดรันเอง — ADR-011): manifest (ชื่อ, เวอร์ชัน, ผู้สร้าง, คำอธิบายที่ AI ใช้เลือก, ตัวอย่างงาน, สิทธิ์ที่ขอ, โมเดลที่ต้องใช้ local/cloud) + คำสั่ง/แม่แบบ + เรียกได้เฉพาะ Action ใน allow-list
2. **AI เลือก Skill เอง** ผู้ใช้ไม่ต้องเลือก โดยเลือกจาก Skill ที่ติดตั้งและเปิดใช้แล้ว **ภายในสิทธิ์ที่บัญชีนั้นอนุญาตไว้แล้ว** · แสดงป้าย "ใช้ Skill: …" พร้อมเหตุผลสั้น ๆ และผู้ใช้เปลี่ยนหรือยกเลิกได้ · ถ้า Skill ต้องการสิทธิ์ใหม่ (ออกเน็ต, ใช้ Cloud, เขียนไฟล์นอกโฟลเดอร์ที่อนุญาต) ต้องขออนุญาตก่อน · ไม่มั่นใจ → ถาม หรือทำโดยไม่ใช้ Skill
3. เนื้อหาของ Skill ที่นำเข้านับเป็นเนื้อหาจากภายนอกตาม 5.6 ข้อ 6 (Skill ที่ไม่มีโค้ดก็ยังแทรกคำสั่งผ่าน prompt ได้) · คำอธิบายที่ใช้เลือกจำกัดความยาว และตรวจการอ้างขอบเขตกว้างเกิน (เช่น "ใช้กับทุกคำขอ") เพื่อไม่ให้ Skill เดียวยึดทุกบทสนทนา
4. AI แนะนำ Skill ใหม่ได้ แต่การนำเข้า/ติดตั้งต้องผ่านหน้าตรวจ: สิทธิ์ที่ขอ (และสิทธิ์ที่เพิ่มจากเวอร์ชันเดิม), ผลตรวจอัตโนมัติ (schema, ขนาด, รูปแบบต้องห้าม), ผู้สร้างและลายเซ็น, ทดลองรันด้วยตัวอย่าง → ผู้ใช้อนุมัติ (โหมดใช้ร่วมกัน: ผู้ดูแลกำหนดได้ว่าต้องให้ผู้ดูแลอนุมัติ) · ไม่ติดตั้งอัตโนมัติ
5. สร้าง ทดลอง (มีชุดตัวอย่าง input และผลที่คาดหวัง) และแชร์ได้ (ส่งออกเป็นแพ็กเกจที่ลงลายเซ็นและไม่มีข้อมูลส่วนตัวติดไป)

**ควรมี**

- ตัวเลือก Skill ที่ประหยัดสำหรับโมเดลเล็ก: กรองด้วย embeddings/คำสำคัญให้เหลือไม่เกิน 3 ตัว แล้วให้ LLM ตัดสิน (โมเดล 1–4B เลือกเครื่องมือพลาดได้บ่อยกว่าโมเดลใหญ่ ต้องวัด)
- เวอร์ชัน ปิดใช้ และย้อนเวอร์ชัน Skill ได้
- Skill ที่มีโค้ด (หลังเฟส 6): รันใน sandbox เช่น bubblewrap + seccomp, ไม่มีเน็ตเป็นค่าเริ่มต้น, จำกัด CPU/RAM, เห็นเฉพาะโฟลเดอร์ที่อนุญาต

**เกณฑ์ผ่าน**

- ชุดประเมินการเลือก Skill ≥ 100 คำขอภาษาไทย (รวมกรณีที่ไม่ควรใช้ Skill) → ความแม่นยำ top-1 ≥ **[ต้องกรอก]**% ต่อโมเดล · ใช้ Skill ที่ต้องการสิทธิ์ที่ยังไม่อนุญาตโดยไม่ถาม = 0 ครั้ง
- Skill ทดสอบที่พยายามอ่าน home ของคนอื่น ออกเน็ต เรียก Action นอก allow-list หรือแทรกคำสั่งผ่านเนื้อหา → ถูกปฏิเสธหรือต้องยืนยัน และบันทึกให้ผู้ใช้เห็น

#### Privacy Center

**ต้องมี**

2. ส่งออกข้อมูลของตัวเองเป็นไฟล์ที่เครื่องอ่านได้ (JSON/Markdown + ไฟล์ต้นฉบับ)

5. ประวัติความยินยอม (ใบหน้า, ผู้ให้บริการ Cloud) และประวัติการส่ง Cloud (เวลา, ผู้ให้บริการ, ขนาด, ค่าใช้จ่าย — ไม่เก็บเนื้อหาซ้ำ)

- ผ่าน canary test เดียวกับ 5.4

### 5.9 ฐานข้อมูลและความเสถียร

**ต้องมี**

1. PostgreSQL (Debian Trixie มาพร้อมเวอร์ชัน 17) + migration ด้วยเครื่องมือเดียว (เช่น Alembic) · ทุก migration ทดสอบ upgrade บนสำเนาข้อมูลก่อน และระบุว่าย้อนได้หรือไม่
2. สิทธิ์ที่ระดับ DB (ADR-004): role ต่อ Linux user เชื่อมต่อผ่าน Unix socket ด้วย peer authentication (DB รู้ตัวตนจากเคอร์เนล) · `ENABLE` + `FORCE ROW LEVEL SECURITY` ทุกตาราง, view ใช้ `security_invoker` · ตั้ง `statement_timeout` และ `CONNECTION LIMIT` ต่อ role (ผู้ใช้ที่มี Terminal ส่ง SQL ตรงได้) · บริการระบบใช้ role ของตัวเอง · แอปห้ามใช้ superuser
3. PostgreSQL ส่วนกลางอยู่นอก home ที่เข้ารหัส จึง: ทุกคอลัมน์ที่เป็นเนื้อหาของผู้ใช้ (ข้อความแชท ชื่อแชท ประวัติคำสั่ง ข้อมูล Skill ชื่อไฟล์ API Key) เข้ารหัสด้วยกุญแจบัญชีก่อนลง DB · ดัชนีค้นหาและ embeddings อยู่ใน home ที่เข้ารหัส (ดู 5.4) · metadata ที่อ่านได้ (เช่น ชื่อบัญชี เวลา) ต้องประกาศใน Privacy Center
4. Backup นอก microSD (ADR-012):
   - เข้ารหัสและลดความซ้ำ (เช่น restic) ไปไดรฟ์ USB/NAS
   - DB ใช้ `pg_dump` ด้วย role ที่มี BYPASSRLS — ปลอดภัยได้เพราะไม่มีเนื้อหาผู้ใช้แบบ plaintext ใน DB (ข้อ 3)
   - ไฟล์ของบัญชีที่เข้ารหัส: ถ้าใช้ fscrypt ระบบอ่านไฟล์ที่ล็อกอยู่ไม่ได้ → backup ได้เฉพาะขณะเจ้าของปลดล็อก (งานในเซสชันของผู้ใช้) · ถ้าใช้ LUKS image ต่อผู้ใช้ → backup ไฟล์ image ขณะไม่ได้ mount ได้ (ADR-003)
   - System Health แสดง backup ล่าสุดรายบัญชี และเตือนบัญชีที่ไม่ได้ backup นาน
   - รหัสของ backup ต้องมีสำเนานอกเครื่อง (พิมพ์หรือ QR) — ถ้ามีแค่ในเครื่อง เครื่องพังแล้วกู้ไม่ได้ ถ้าเก็บไว้คู่กับไดรฟ์ backup ใครได้ไดรฟ์ก็ได้ข้อมูล
5. ทดสอบ restore จริงเป็นรอบ: อัตโนมัติรายเดือน = `restic check --read-data-subset` + กู้ตัวอย่างไปไว้บนไดรฟ์ backup (microSD 64GB อาจมีที่ไม่พอ) + `pg_restore` ลง DB ชั่วคราว + query ตรวจ · การเปิดอ่านข้อมูลที่เข้ารหัสทดสอบด้วยบัญชีทดสอบที่ทีมรู้รหัส · ก่อนออกเวอร์ชันต้องกู้ลง microSD ใหม่ทั้งเครื่อง · System Health แสดง "ทดสอบ restore สำเร็จล่าสุด"
6. พื้นที่เต็ม: เตือนที่ 80% · ที่ 90% หยุดงานที่ไม่จำเป็น (ดาวน์โหลดโมเดล, ทำดัชนี, cache) และปฏิเสธไฟล์ใหม่พร้อมบอกเหตุผล · กันพื้นที่ฉุกเฉินให้ DB · โควตารายบัญชี
7. บริการล้ม: systemd `Restart=on-failure` + backoff, health check, hardware watchdog · UI แสดง "บางส่วนใช้ไม่ได้" แทนการค้างทั้งระบบ
8. อุปกรณ์หลุด (กล้อง, ไมค์, ไดรฟ์ backup, SSD แบบ USB): รับเหตุการณ์จาก udev ไม่ crash · backup ที่ค้างถูกทำเครื่องหมายว่าล้มเหลวแล้วลองใหม่
9. ปิดเครื่องผิดปกติ: ห้ามปิด `fsync`, `full_page_writes` หรือ `synchronous_commit` เพื่อความเร็ว · เขียนไฟล์แบบ atomic (ไฟล์ชั่วคราว → fsync → rename) · หลังบูตแจ้งผลการตรวจให้ผู้ใช้รู้
10. ติดตั้ง/อัปเดต/ย้อนเวอร์ชันของแอป (ADR-009): แต่ละ release อยู่คนละโฟลเดอร์ (รวม venv และ Qt) + symlink `current` · ก่อนอัปเดต backup + ตรวจพื้นที่ + ตรวจลายเซ็นแพ็กเกจ · migration แบบ expand/contract (เวอร์ชันเก่ายังทำงานกับ schema ใหม่ได้จนกว่าจะยืนยัน) · health check ไม่ผ่าน → สลับกลับอัตโนมัติ · ถ้ามี migration ที่ย้อนไม่ได้ ต้องบอกผู้ดูแลก่อนกดอัปเดตว่าการย้อนต้องกู้จาก backup
11. อัปเดต OS/เคอร์เนล/EEPROM/PostgreSQL (ADR-013): ไม่ล็อกเวอร์ชันจนช่องโหว่ค้าง · ติดตั้งชุดอัปเดตความปลอดภัยที่ทดสอบกับ release ปัจจุบันแล้วเมื่อผู้ดูแลยืนยัน · backup ก่อนเสมอ · ย้อนได้เฉพาะแอป (OS ย้อนด้วย backup หรือ A/B ภายหลัง) · PostgreSQL คงเวอร์ชันหลักตาม Debian release การขึ้นเวอร์ชันหลักต้องมีแผน `pg_upgrade` หรือ dump/restore + backup
12. จำกัด logs (เช่น journald ≤ 200 MB), cache, จำนวนโมเดล และงานเบื้องหลังตามงบในหัวข้อ 6

**ควรมี**

- ปรับ PostgreSQL ให้เขียนน้อยลงโดยไม่ลดความทนทาน (เช่น `wal_compression`, ขยาย `checkpoint_timeout`) และ mount แบบ `noatime`
- A/B rootfs (tryboot ของ Raspberry Pi หรือ RAUC) เป็นทางเลือกระยะยาว — ซับซ้อนและกินพื้นที่มากบน 64GB

**เกณฑ์ผ่าน**

- ดึงปลั๊กแบบสุ่มระหว่างเขียนหนัก (≥ 20 ครั้งในเฟส 1, ≥ 50 ครั้งก่อน pilot) → บูตได้ทุกครั้ง, DB สมบูรณ์, ข้อมูลหายไม่เกินรอบ autosave ล่าสุด
- เติมพื้นที่จนเต็ม → ยังเข้าระบบได้, ข้อความเตือนถูกต้อง, DB ไม่เสีย
- `kill -9` ทีละบริการ → กลับมาเองภายในเวลาที่ตั้ง และ UI ไม่ค้าง
- ถอดไดรฟ์ backup กลางคัน → รอบนั้นถูกทำเครื่องหมายล้มเหลว, รอบถัดไปสำเร็จ, repo ผ่าน check
- ซ้อมอัปเดตที่มี migration แล้วย้อนกลับ → ข้อมูลครบ
- ซ้อมกู้ทั้งเครื่องจาก backup ลงการ์ดใหม่ รวมถึงผู้ใช้ปลดล็อกข้อมูลตัวเองด้วยรหัสผ่านหรือรหัสกู้คืนได้
- ใช้งานต่อเนื่อง 72 ชม. (soak test) → ไม่มีหน่วยความจำที่โตขึ้นเรื่อย ๆ

## 6. งบทรัพยากร (ค่าประมาณ — ต้องแทนด้วยค่าที่วัดได้)

### 6.1 RAM (8 GB)

| ส่วนประกอบ | RAM โดยประมาณ | ทำงานเมื่อไร |
|---|---|---|
| ระบบพื้นฐาน (OS + labwc + บริการของเรา) | 0.8–1.2 GB | ตลอด |
| UI Shell (Qt Quick + PySide6) | 0.2–0.4 GB | ตลอด |
| PostgreSQL (ปรับให้เล็ก) | 0.1–0.3 GB | ตลอด |
| ตรวจใบหน้า/เจ้าของ (YuNet + SFace + PAD) | 0.1–0.3 GB | ระหว่างเซสชัน |
| STT | whisper.cpp small ~0.85 GB (ตามตารางของ whisper.cpp) · NeMo/PyTorch อาจเกิน 1 GB | เมื่อเปิดใช้เสียง |
| TTS (VITS ขนาดเล็ก) | 0.1–0.4 GB | เมื่อเปิดอ่านออกเสียง |
| LLM ~1B Q4 | ~1 GB | เมื่อใช้แชท (โมเดลค่าเริ่มต้นโหลดค้าง) |
| LLM ~3–4B Q4 + context 4K | ~2.8–3.6 GB | เมื่อใช้แชท |
| Chromium (ไม่กี่แท็บ) | 0.5–2 GB ขึ้นไป | ตามผู้ใช้ |
| OCR / embeddings | 0.2–0.8 GB | งานเบื้องหลัง |
| Guest home บน tmpfs | ตามขนาดที่จำกัด | เฉพาะเซสชัน Guest |

รวมกรณีเปิดทุกอย่างพร้อมกันเกิน 8 GB ได้ จึงต้องมีตัวจัดทรัพยากร (resourced) ที่ทำตามกติกานี้:

1. แบ่ง 3 ชั้น: **(ก) สำคัญตลอด** UI, การยืนยันตัวตน, การตรวจเจ้าของ — กันทรัพยากรไว้เสมอ · **(ข) งานโต้ตอบหนัก** LLM, STT, TTS — ได้ก่อน · **(ค) งานเบื้องหลัง** OCR, ทำดัชนี, embeddings, backup, ดาวน์โหลดโมเดล — รันเมื่อว่าง ใช้ nice/ionice และ cgroup จำกัด CPU และหยุดเมื่อผู้ใช้กลับมาใช้งาน
2. งานชั้น (ข) รันพร้อมกันได้เฉพาะคู่ที่วัดแล้วว่าไหว (เช่น LLM สร้างข้อความ + TTS อ่านทีละประโยค)
3. ก่อนโหลดโมเดลตรวจ RAM ว่าง ถ้าไม่พอให้ปลดโมเดลที่ไม่ใช่ค่าเริ่มต้นและว่างนานที่สุดก่อน แล้วบอกผู้ใช้ตามจริง
4. โมเดลค่าเริ่มต้นโหลดค้างไว้ (หรือโหลดล่วงหน้าหลัง Login) · โมเดลอื่นปลดเมื่อไม่ได้ใช้เกินเวลาที่ตั้ง (เช่น 10 นาที)
5. ใช้ zram ไม่ใช้ swap บน microSD · เฝ้าแรงกดหน่วยความจำ (PSI) และตั้ง systemd-oomd ให้ยุติงานเบื้องหลังก่อน UI และการยืนยันตัวตนเสมอ
6. เฝ้าอุณหภูมิและ `vcgencmd get_throttled` (ไฟตก/ร้อนเกิน) → ชะลองานเบื้องหลังและแจ้งใน System Health

### 6.2 พื้นที่ (microSD 64 GB ใช้ได้จริงราว 59 GB)

| หมวด | งบโดยประมาณ |
|---|---|

## 7. สถาปัตยกรรมที่แนะนำ (โต้แย้งได้ด้วยหลักฐาน)

```text
Power on → systemd → greetd → Greeter (Qt/QML, user: greeter)
                                 │ PAM: password / recovery code / face helper
                                 ▼
User session (runs as the user's UID)
  labwc (Wayland compositor)
  ├─ AIPC Shell (QML UI) ◄──► Session Agent (Python, user's UID)
  │                            holds the account data key in memory
  ├─ Browser / Terminal / Desktop (user's UID, per policy)
  └─ Shield / Lock client (ext-session-lock-v1)
        │
        │ Unix sockets (caller UID checked with SO_PEERCRED)
        ▼
System services
  authd       accounts, device-mode policy, audit    (minimal root helper)
  visiond     owns the camera: detect / recognize / PAD → events only
  resourced   heavy-job queue, model load/unload, RAM & thermal watch
  ai-workers  llama-server, stt, tts, ocr, embed     (no network, Unix sockets,
              restarted at every logout)
  cloudgw     the only AIPC service that may call AI APIs; needs a
              per-request consent token and checks the destination host
  postgresql  peer auth + FORCE row-level security
  backupd     encrypted backups (egress only to the NAS, if configured)
  updated     app / OS updates after admin approval  (minimal root helper)
```

**กติกาของสถาปัตยกรรม**

1. backend ตัดสินสิทธิ์จาก UID ที่เคอร์เนลยืนยัน (SO_PEERCRED / peer auth) ไม่เชื่อค่าที่ UI ส่งมา · งานผู้ดูแลผ่าน polkit + ยืนยันรหัสผ่าน · ผู้ใช้ที่มี Terminal ยิง socket ของ backend ได้เอง จึงห้ามถือว่าการซ่อนปุ่มคือการป้องกัน · รูปแบบ IPC ตาม ADR-008
2. บริการที่ต้องใช้ root (ส่วนสร้างบัญชีของ authd และ updated) แยกเป็น helper ที่เล็กที่สุดและ sandbox ด้วย systemd · บริการอื่นรันเป็น system user ของตัวเอง
3. "ไม่ส่ง Cloud อัตโนมัติ" บังคับ 3 ชั้น: UI ขอยืนยัน → cloudgw ต้องได้ consent token ที่ผูกกับคำขอนั้นและตรวจชื่อโฮสต์ปลายทางเอง → nftables ตาม cgroup: บริการของ AIPC ไม่มีเน็ต ยกเว้น cloudgw, updated และตัวดาวน์โหลดโมเดล (เมื่อผู้ดูแลสั่ง), backupd (เฉพาะ NAS) และบริการพื้นฐานของ OS (DNS, NTP) · nftables กรองตาม IP/cgroup ไม่ใช่ชื่อโดเมน (API ของ AI อยู่บน IP ของ CDN ที่ใช้ร่วมกัน) การตรวจชื่อโฮสต์จึงอยู่ที่ cloudgw
4. AI workers ไม่มีเน็ต: คุยผ่าน Unix socket หรือใช้ `IPAddressDeny=any` + `IPAddressAllow=localhost` (ถ้าใช้ `PrivateNetwork=yes` บริการอื่นจะต่อ TCP เข้า worker ไม่ได้) · สุขอนามัยของ worker ตาม 5.2 ข้อ 6
5. Browser/Terminal ของผู้ใช้ออกเน็ตตามปกติ — สิ่งที่ผู้ใช้ทำเองไม่นับเป็น "การส่งอัตโนมัติ" แต่โค้ดของ AIPC ห้ามใช้ช่องทางนั้นส่งข้อมูล
6. ภาพจากกล้องไม่ออกจาก visiond ส่งออกเป็นเหตุการณ์เท่านั้น (เช่น OWNER_PRESENT, OTHER_PERSON)
7. ความลับถอดรหัสเฉพาะในโปรเซสที่ต้องใช้และเฉพาะระหว่างเซสชัน · API Key ส่งให้ cloudgw ต่อคำขอ ไม่เก็บค้างที่ cloudgw
8. งานหนักทุกชิ้นผ่าน resourced · UI ไม่ทำงานหนักเอง
9. greeter เขียนเองเพื่อรองรับ flow ใบหน้า (ดู QtGreet เป็นตัวอย่างได้) · ตัวล็อกฝั่ง Qt ต้อง spike ก่อน เช่น qt-session-lock (GPL-3.0 โปรเจกต์เล็ก) หรือเขียน client ของ ext-session-lock เอง

## 9. การทดสอบและระดับหลักฐาน

| ระดับ | ความหมาย | หลักฐานขั้นต่ำ |
|---|---|---|
| 0 ยังไม่ทำ | — | — |
| 1 ออกแบบแล้ว | มี spec หรือ ADR | ลิงก์เอกสาร |
| 2 ต้นแบบ | มีโค้ดทำงานได้บางส่วน | commit + วิธีรัน |
| 3 ผ่านบนเครื่องพัฒนา | unit/integration test ผ่าน | ผลเทสต์ + commit |
| 4 ยืนยันบน Pi 5 | ผ่านเกณฑ์ในเอกสารนี้บน Pi จริง | รายงาน (วันที่, commit, ฮาร์ดแวร์, ค่าดิบ) |
| 5 ผ่าน pilot | ผู้ใช้จริงใช้ตามแผนที่กำหนด | รายงาน pilot |

- "พร้อมใช้" ของเฟสใด = ทุกข้อ **ต้องมี** ในเฟสนั้นอยู่ระดับ 4 ขึ้นไป · ห้ามใช้คำว่า "พร้อม 100%"
- หลักฐานผูกกับ commit ถ้าโค้ดส่วนนั้นเปลี่ยน สถานะต้องกลับไปรอตรวจซ้ำ
- **หมายเหตุสถิติ:** "0 ครั้งจาก N ครั้ง" ไม่ได้แปลว่าเสี่ยง 0% — ขอบบนที่ความเชื่อมั่น 95% ≈ 3/N (0 จาก 30 ยังเข้ากันได้กับอัตราจริงถึงราว 10% · จะอ้าง ≤ 5% ต้องลอง ≥ 60 ครั้งแล้วไม่สำเร็จเลย)
- วิธีวัดประสิทธิภาพ: ระบุฮาร์ดแวร์ (ไฟ, cooler, รุ่น SD/SSD), OS/kernel, commit, ไฟล์โมเดล + hash, จำนวน threads · warm-up 1 ครั้ง แล้ววัด ≥ 5 ครั้ง รายงาน median และ p95 · บันทึกอุณหภูมิและ `vcgencmd get_throttled` · เก็บค่าดิบ (CSV/JSON) ไว้ใน repo

## 11. กติกาการทำงานสำหรับ AI และผู้พัฒนา

**สิ่งที่ขอในรอบแรก (ก่อนเขียนฟีเจอร์ใหม่)**

1. ตรวจโค้ดและเอกสารที่มีอยู่ แล้วทำ STATUS.md ตามระดับหลักฐานในหัวข้อ 9 (มีแล้ว / ต้นแบบ / ยังไม่ทำ / ต้องทดสอบบน Pi)
2. ประเมินความเป็นไปได้รายหมวดอย่างตรงไปตรงมา: อะไรทำได้แน่, อะไรทำได้แต่ต้องยอมรับข้อจำกัด, อะไรไม่ควรสัญญา
3. แผนเฟส 0 (spike) พร้อมวิธีวัดและเกณฑ์ตัดสินของแต่ละ ADR
4. ข้อโต้แย้งต่อ brief นี้ (ถ้ามี) พร้อมหลักฐาน

**กติกา**

1. **ตรวจของจริงก่อน:** อ่านโค้ด เอกสาร และสคริปต์ที่มีอยู่ แล้วรายงานสิ่งที่พบพร้อม path ก่อนเสนอหรือแก้
2. จัดสถานะตามระดับหลักฐานในหัวข้อ 9 · ห้ามอ้างว่าพร้อมจากการมีโค้ดหรือผ่าน unit test อย่างเดียว
3. ตัวเลขประสิทธิภาพต้องมาจากการวัดบน Pi หรือระบุชัดว่าเป็น "ประมาณการ/อ้างอิงภายนอก"
4. ก่อนเปลี่ยนโครงสร้างใหญ่ (schema, ที่เก็บข้อมูล, auth, การเข้ารหัส, การจัดโฟลเดอร์ข้อมูล): เสนอแผน + จุดย้อนกลับ (git tag, backup ที่ทดสอบ restore แล้ว, ขั้นตอนย้อน) แล้วรออนุมัติ
5. ห้ามทำข้อมูลเดิมหาย: migration ต้องมี backup ก่อน ทดสอบบนสำเนา และมีวิธีตรวจหลังย้าย
6. ไม่ใส่ความลับในโค้ด เทสต์ หรือ log · เทสต์ใช้ canary
7. ตรวจไลเซนส์ทั้งโค้ดและน้ำหนักโมเดลก่อนเลือกใช้ (ตาม ADR-014)
8. ฟีเจอร์ใหม่ต้องบอกต้นทุน RAM/CPU/พื้นที่ และเกณฑ์ทดสอบ (รูปแบบเดียวกับหัวข้อ 6.3) · เลือกทางที่เรียบง่ายและดูแลได้ก่อน
9. ข้อเสนอเพิ่มเติมรวบรวมไว้ท้ายรายงานครั้งเดียว แยกเป็น "ควรทำตอนนี้ / ภายหลัง / ไม่ควรทำ" พร้อมเหตุผล
