# ข้อเสนอรอบ 3: ตัดขอบเขตให้เหลือระบบที่เสถียรบน Pi 5 8GB

> เขียน 2026-09-28 · **สถานะ: อนุมัติแล้ว 2026-09-28 (Pakon) พร้อมแก้ 2 ข้อ:**
> (1) **เก็บการสมัครที่หน้า Login** — สร้าง Linux account จริง ผู้ดูแลใส่รหัสผ่านยืนยันที่หน้าสมัครทันที ·
> (2) **เก็บรหัสกู้คืน** — ลืมรหัสผ่าน → ใช้รหัสกู้คืนตั้งรหัสใหม่ที่หน้า Login · ออกแบบในการ์ด 0012

> ที่มา: Pakon ขอ "ลดฟีเจอร์ที่ไม่จำเป็น แล้วหาวิธีทำให้ระบบดีและเสถียรที่สุด เหมาะกับ Pi 5 8GB จริง ๆ"
> ข้อมูลที่ใช้: repo commit `4ea56e6` · เทสต์ 337 ผ่าน (ข้าม 8) · ผลตรวจโค้ด 2026-09-28 ·
> ผลวัดของผู้อื่นบน Pi 5 (ลิงก์ในหัวข้อ 11 — ใช้เลือกผู้สมัครเท่านั้น ห้ามใส่บทที่ 4 แทนผลของเรา)

## สรุป (อ่านแค่ส่วนนี้ก็ได้)

1. **เครื่องมือที่เลือกไว้ถูกแล้ว ไม่ต้องเปลี่ยน** — Qt/QML (PySide6), greetd + PAM, labwc, OpenCV, llama.cpp
   เป็นตัวที่เบาและมีคนใช้บน Pi มาก · ปัญหาของโปรเจกต์คือ **ขอบเขต** ไม่ใช่ stack
2. **เหลือ 3 ข้ออ้างที่วัดได้บน Pi 5** (หัวข้อ 2) แทน 9 หมวดของ BRIEF
3. **เพิ่มของใหม่แค่อย่างเดียว: แชทกับ LLM ในเครื่อง** — ตอนนี้ส่วน "AI" ของ AI Personal Computer ยังไม่มีเลย
4. **ตัด 12 หมวด** ไปเป็นงานต่อยอดในบทที่ 5 (หัวข้อ 5) และ **ลบของที่ยังไม่พร้อมออกจากหน้าจอ** แทนการขึ้นว่า "ยังไม่พร้อม"
5. ADR ที่ต้องตัดสินก่อนเฟส 1 (7 ข้อ) **ตัดสินได้ทันที** เพราะขอบเขตเล็กลง เหลือรอแค่ผล spike LLM (หัวข้อ 6)
6. **หยุดเพิ่มฟีเจอร์ 12 ต.ค.** หลังจากนั้นทดสอบ วัดผล และเขียนเล่มเท่านั้น

## 1. หลักที่ใช้ตัดสินว่าเก็บหรือตัด

ฟีเจอร์อยู่ต่อเมื่อผ่าน **ครบทั้ง 4 ข้อ**:

1. จำเป็นต่อข้ออ้างของเล่ม (หัวข้อ 2) หรือทำเสร็จระดับ 3 แล้วและยืนยันบน Pi 5 ได้ในไม่กี่ชั่วโมง
2. ถึงระดับ 4 บน Pi 5 ได้ก่อน 12 ต.ค.
3. ไม่เพิ่มบริการที่ต้องรันตลอดเวลา นอกจาก LLM หนึ่งโปรเซส
4. Pakon อธิบายให้กรรมการฟังเองได้ทุกส่วน (docs/ROLE.md)

## 2. ข้ออ้างของเล่มหลังตัด (3 ข้อ)

| ข้ออ้าง | อะไรพิสูจน์ | วัดอะไรบน Pi 5 |
|---|---|---|
| **1. AI ภาษาไทยทำงานในเครื่องได้จริง** | แชทกับ LLM บน Pi 5 8GB ใช้ได้ตอนไม่มีเน็ต และไม่มีข้อมูลออกนอกเครื่อง | เวลาถึงคำแรก · token/วิ · RAM สูงสุด · อุณหภูมิ/throttle 10 นาที · นับการเชื่อมต่อขาออก 30 นาที |
| **2. หลายคนใช้เครื่องเดียวกันได้ ข้อมูลแยกกันที่ระดับ OS** | 1 คน = 1 Linux account (greetd + PAM) · ข้อมูลอยู่ใน home 0700 · AI ของแต่ละคนเป็นโปรเซสของคนนั้นและปิดเมื่อออกจากระบบ | ชุดทดสอบข้ามบัญชี (B อ่านแชท/แม่แบบใบหน้า/socket ของ A ไม่ได้) · หลังออกจากระบบไม่เหลือโปรเซส |
| **3. งานที่ต้องถูกแน่นอนใช้โค้ด ไม่ใช้ LLM และระบบทนต่อความผิดพลาด** | สกิลนัดหมาย/สั่งเครื่อง/ถามเครื่องแบบกฎ (H6) + ทดสอบความทนทาน | ความแม่นยำผ่านเส้นทางจริงของผู้ใช้ · ทำผิดโดยไม่ถาม · injection · soak 12 ชม. · kill / ถอดกล้อง / ดึงปลั๊ก |

ระบบใบหน้า (การ์ด 0005–0011) อยู่ต่อในฐานะส่วนประกอบที่มีผลวัดดีอยู่แล้ว (LFW 99.35%) — ลงทะเบียน/ทดลอง/ลบในหน้าตั้งค่า
การใช้ใบหน้าเลือกบัญชีที่หน้า Login **ตัดออกจากรุ่นนี้** (เวลาไปใช้กับการสมัครจริง + รหัสกู้คืนแทน — หัวข้อ 10)

## 3. ระบบหลังตัด (ภาพเดียว)

```text
เปิดเครื่อง → systemd → greetd → หน้า Login ของเรา (ผู้ใช้ _greetd) → PAM ของ OS ตรวจรหัสผ่าน
   │
   ▼ เซสชันของผู้ใช้คนนั้น (UID ของเขาเอง)
   labwc ─► aipc.ui  หน้าจอ + สกิลแบบกฎ + ใบหน้า ──HTTP ผ่าน Unix socket──► llama-server (โมเดลเดียว)
                                                   $XDG_RUNTIME_DIR/aipc/llm.sock
                                                   (โฟลเดอร์ 0700 ของผู้ใช้ → คนอื่นต่อไม่ได้ OS กันให้)
   "ออก" ─► ปิดทุกโปรเซสของผู้ใช้ (KillUserProcesses=yes) ─► กลับหน้า Login

ข้อมูลทั้งหมดอยู่ใน home ของผู้ใช้ (0700) เขียนแบบ atomic:
   ~/.config/aipc/ui.json · ~/.local/share/aipc/{reminders.json, chats/, face-template.json}
ไม่มีโปรแกรมของเราเปิดพอร์ตเครือข่าย · ไม่มีฐานข้อมูล · ไม่มี Cloud
```

ระหว่างเซสชันมีโปรเซสของเราแค่ **2 ตัว**: หน้าจอ และ LLM · LLM ที่หนักและพังง่ายแยกออกมา
ถ้า LLM พัง หน้าจอยังอยู่และบอก "AI กำลังเริ่มใหม่" · ถ้าหน้าจอพัง `aipc-shell-loop` เปิดใหม่ให้ (มีอยู่แล้ว)

**llama-server รองรับ Unix socket** (`--host` ที่ลงท้ายด้วย `.sock`) · ปิดหน้าเว็บในตัว (`--no-webui`)
และหน้าดูสถานะ slot (`--no-slots`) · รันเป็น user service ของ systemd (`Restart=on-failure`, `MemoryMax`)
— ต้องยืนยันกับ build ที่ใช้จริงบน Pi 5 ในขั้น spike

→ เกณฑ์ออกจากเฟส 0 ("ADR ก่อนเฟส 1 ตัดสินครบ") เป็นจริงได้ภายใน **5 ต.ค.** ถ้า spike LLM เสร็จ

## 7. เลือก LLM: ของที่มีคนวัดบน Pi 5 แล้ว + เกณฑ์ที่ประกาศก่อนวัด

### 7.1 ผลวัดของผู้อื่น (ใช้เลือกผู้สมัครเท่านั้น)

| โมเดล | สร้างข้อความ (tok/s) | อ่าน prompt (tok/s) | RAM | ที่มา |
|---|---|---|---|---|
| Gemma 3 1B Q4_K_M | ~10 | ~25 | ~1.1 GB | Kunal Ganglani, Pi 5 (Ollama) |
| Gemma 3 1B Q4_K_M (llama-bench 4 threads) | ~14 | ~46 | — | BRIEF 5.4 |
| Gemma 4 E2B Q4 (llama.cpp build บนเครื่อง + ปรับค่า) | 7 | 20 | — | note.com/ai_meg, Pi 5 |
| Llama 3.2 3B | 4.61 | — | — | Jeff Geerling, Pi 5 8GB (CPU) |
| Qwen2.5 3B | ~6 | ~29 | — | BRIEF 5.4 (Pi 5 16GB) |
| Gemma 3 4B Q4_K_M | ~3.5 | ~8 | ~3.8 GB | Kunal Ganglani, Pi 5 8GB (Ollama) |
| Gemma 3 4B QAT | ~5 | ~12 | ~2.8 GB | Kunal Ganglani, Pi 5 8GB (Ollama) |

**อ่านตารางนี้ยังไง:**
- โมเดล 1–2B สร้างได้ราว 7–14 tok/s (เร็ว แต่ภาษาไทยมักอ่อนกว่า) · 3–4B ราว 3.5–6 tok/s (อ่านตามทันขณะมันพิมพ์)
- **คอขวดจริงคือการอ่าน prompt:** 4B อ่านได้ 8–12 tok/s → prompt 200 token ใช้ 17–25 วิถ้าเริ่มจากศูนย์
  จึงต้องใช้ system prompt สั้น + prompt cache ของ llama-server (อ่านส่วนที่ซ้ำครั้งเดียวต่อเซสชัน)
- **build บนเครื่องสำคัญมาก:** ในการทดลองของ note.com binary สำเร็จรูปได้ 1.5 tok/s · build บน Pi 5 เองได้ 6 ·
  ปรับค่าเพิ่ม (KV cache แบบ q4_0, hugepages, CPU governor) ได้ 7 — runbook เดิม build บนเครื่องอยู่แล้ว
- ตัวเลขต่างกันตามเครื่องมือ (Ollama กับ llama.cpp) · token ของแต่ละโมเดลตัดภาษาไทยไม่เท่ากัน
  → รายงาน "ตัวอักษรไทยต่อวินาที" คู่กับ tok/s ด้วย เพื่อเทียบข้ามโมเดลได้ยุติธรรม

### 7.2 ผู้สมัคร 3 ตัว (ไลเซนส์ Apache-2.0 ทั้งหมด → ADR-014 ง่าย)

| ชั้น | โมเดล | ทำไม |
|---|---|---|
| เร็ว | **Gemma 4 E2B-it** | มีคนวัดบน Pi 5 ด้วย llama.cpp แล้ว · ใหม่ (2026) · แต่ model card ไม่ได้ระบุภาษาไทยชัด ต้องวัดคุณภาพไทยเอง |
| ไทย | **Typhoon2.5-Qwen3-4B** | ปรับจูนภาษาไทยโดย SCB 10X · มี GGUF ทางการ |
| เทียบ | **Qwen3-4B-Instruct-2507** | ฐานเดียวกับ Typhoon2.5 → วัดได้ตรง ๆ ว่าการปรับจูนไทยช่วยแค่ไหน (ได้ตารางดี ๆ ในบทที่ 4) |

ตัวสำรองถ้า E2B หนักเกิน: Gemma 3 1B (มีผลวัดบน Pi 5 มากที่สุด) · ไม่ใช้ Qwen3.5 ในรอบนี้ เพราะใช้ attention
แบบใหม่ (Gated DeltaNet) ที่ยังไม่พบผลวัดบน CPU ของ Pi 5

### 7.3 เกณฑ์ตัดสิน (ประกาศก่อนวัด · H9)

เลือกตัวที่ **คะแนนภาษาไทยสูงสุด** ในกลุ่มที่ผ่านครบทุกข้อ:

1. ชุดคำถามไทย 30 ข้อของเรา (เขียนและ commit ก่อนวัด) ให้คะแนน 1–5 โดย 2 คน → เฉลี่ย ≥ **3.5** *(ค่าเสนอ)*
2. เวลาถึงคำแรก prompt 200 token ≤ **10 วิ** (ชั้น 4B) / ≤ **5 วิ** (ชั้นเร็ว) — ตาม BRIEF 5.4
3. สร้างข้อความ ≥ **4 tok/s** *(ค่าเสนอ)*
4. RAM สูงสุด ≤ **3.5 GB** ที่ context 4096 (เหลือที่ให้หน้าจอ ใบหน้า และ Chromium)
5. ตอบต่อเนื่อง 10 นาที (มี Active Cooler): `get_throttled` = 0x0 และความเร็วลดไม่เกิน 10%

ไม่มีตัวไหนผ่านครบ → เลือกตัวที่ผ่านข้อ 2–5 และคะแนนไทยสูงสุด แล้วเขียนข้อจำกัดตรง ๆ
หลังเลือกแล้วลองปรับทีละอย่าง: threads 3 เทียบ 4 (เลือก 3 ถ้าช้าลงไม่เกิน 15% เพราะหน้าจอลื่นกว่า) · Q4_0 เทียบ Q4_K_M

## 8. ทำให้เสถียร 10 ข้อ

1. **หยุดเพิ่มฟีเจอร์ 12 ต.ค.** — หลังจากนั้นแก้บั๊ก วัดผล เขียนเล่มเท่านั้น
2. **ติดตั้งซ้ำได้เหมือนเดิมทุกครั้ง** — ไฟล์ constraints ล็อกเวอร์ชัน PySide6/OpenCV/numpy (เอาจาก venv บน Pi 4 ที่ใช้ได้แล้ว) ·
   ล็อก commit ของ llama.cpp · ล็อก sha256 ของไฟล์โมเดล · บันทึกทุกเวอร์ชันในรายงานผลวัด
   (ตอนนี้ตัวเลขใบหน้าวัดด้วย OpenCV 5.0.0 แต่การ์ด 0011 บน Pi 5 ใช้ 4.10)
3. **แยกส่วนที่หนักและพังง่าย** — LLM เป็น user service ของ systemd (`Restart=on-failure`, `MemoryMax`) ·
   LLM พัง = หน้าจอบอก "AI กำลังเริ่มใหม่" ไม่ล่มทั้งเซสชัน
4. **หน้า Login ต้องไม่หาย** — อัปเดตแบบโฟลเดอร์ต่อรุ่น → ลองเปิดหน้า Login ด้วยผู้ใช้ `_greetd` แบบ offscreen ก่อน →
   สลับด้วย symlink ทีเดียว → ย้อนด้วยคำสั่งเดียวไม่ต้องใช้เน็ต · ปิด Ctrl+Alt+Q ที่หน้า Login · ปิด autologin ·
   คงทางเข้าสำรอง tty2 + SSH ไว้เสมอ
5. **ออกจากระบบ = ปิดทุกอย่างของผู้ใช้** — `KillUserProcesses=yes` → AI ของคนก่อนไม่ค้าง ไม่กิน RAM คนถัดไป
6. **ข้อมูลไม่เสียเมื่อไฟดับหรือดิสก์เต็ม** — ตัวเขียนไฟล์แบบ atomic ตัวเดียวใช้ทุกที่ (ตั้งค่า นัด ใบหน้า แชท) ·
   แก้บั๊ก `.bak` ที่ทับไฟล์สำรองดี · ดิสก์เต็ม = บอกผู้ใช้ ไม่หายเงียบ
7. **ไม่แย่ง CPU กับ LLM** — เลือก threads จากการวัด · ไม่มีแอนิเมชันที่วนไม่หยุดระหว่าง AI ตอบ
   (รอบแรกวัดบน Pi 4 ไว้ว่าทำให้ LLM ช้าลงราวครึ่งหนึ่ง) · ใช้ zram ของ Trixie ตามค่าเริ่มต้น · จำกัดขนาด journald
8. **ตรวจฮาร์ดแวร์ก่อนวัดทุกครั้ง** — อะแดปเตอร์ 27W + Active Cooler · `aipc.doctor` ด้านไฟต้องไม่ "ไม่ผ่าน"
9. **ทดสอบเส้นทางที่ผู้ใช้เจอจริง** — เพิ่มเทสต์ end-to-end (ข้อความ → ตัวคัดสกิล → การ์ดที่ผู้ใช้เห็น) ·
   ทุกบั๊กต้องมีเทสต์ที่แดงก่อนแก้ · วัดผลสกิลผ่านเส้นทางจริง ไม่ใช่แค่ตัวแปล (ตัวเลข 40/40 เดิมวัดแค่ตัวแปลงวันเวลา)
10. **กันวันสอบพัง** — ทำ image ของการ์ดที่ใช้ได้ + การ์ดสำรองที่ flash image เดียวกัน + ขั้นตอนกู้คืนพิมพ์ติดเครื่อง

## 11. สิ่งที่ต้องให้ Pakon ตัดสิน

ตัดสินแล้ว 2026-09-28: รายการเก็บ/ตัดอนุมัติ · สมัครอยู่ที่หน้า Login (ผู้ดูแลยืนยันทันที) · เก็บรหัสกู้คืน

ยังรอ:
1. อาจารย์ที่ปรึกษากำหนดฟีเจอร์ไหนเป็นข้อบังคับบ้าง (รายงานรอบแรกบันทึกว่าอาจารย์ขอ Skill — แผนนี้เก็บ Skill ไว้ 4 ตัว)
2. ผู้สมัคร LLM 3 ตัว และเกณฑ์ในหัวข้อ 7.3 (โดยเฉพาะค่าเสนอ: คะแนนไทย ≥ 3.5 และ ≥ 4 tok/s)
3. วันหยุดเพิ่มฟีเจอร์ 12 ต.ค. — เล่มเขียนไปถึงไหนแล้ว (ถ้ายังไม่เริ่ม ต้องเลื่อนวันหยุดฟีเจอร์ให้เร็วขึ้น)
4. มี microSD สำรองสำหรับ T10/T13 และสำหรับทำ image ไหม (STATUS บอกว่ามีใบสำรอง)
5. อนุมัติการ์ด 0012 (สมัครจริง + รหัสกู้คืน) ก่อนเริ่มเขียนโค้ด
