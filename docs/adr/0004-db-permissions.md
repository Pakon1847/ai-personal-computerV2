# ADR-004: สิทธิ์ใน DB + ที่อยู่ของข้อมูล

- **สถานะ:** **ตัดสินแล้ว 2026-09-28** (Pakon · ขอบเขตรอบ 3)
- **ต้องตัดสินก่อน:** เฟส 1

## ค่าที่ brief แนะนำ

role ต่อ Linux user (peer auth) + FORCE RLS · เนื้อหาผู้ใช้เข้ารหัสด้วยกุญแจบัญชี · ดัชนีค้นหาอยู่ใน home ที่เข้ารหัส

## หลักฐานที่ใช้ตัดสิน

**Pi 4 (2026-09-24):** ผ่าน 13 · ไม่ผ่าน 0 · สังเกต 2 · PostgreSQL 17.11 ([ผล](../benchmarks/2026-09-24-pi4-pg-rls.md)) · spike: [`spikes/pg-rls/run.sh`](../../spikes/pg-rls/run.sh) (ROADMAP 0.6)

**เกณฑ์ตัดสิน (ประกาศก่อนวัด):** กรณี "ผ่าน/ไม่ผ่าน" ทั้ง 13 กรณีใน spike ต้องผ่านครบบน Pi 4 แล้วยืนยันซ้ำบน Pi 5
ถ้ามีกรณีใดไม่ผ่าน → แนวทาง peer auth + FORCE RLS ใช้ไม่ได้ตามที่ brief เสนอ ต้องกลับมาทบทวน ADR นี้

**สองกรณี "สังเกต" ที่ต้องเขียนในเล่ม:**

- กรณี 13 view ที่ไม่มี `security_invoker` — ผลจะบอกว่าทำไม brief บังคับให้ใช้ security_invoker
- กรณี 15 superuser อ่านได้ทุกแถว — เป็นเรื่องที่คาดไว้ RLS ไม่กัน root/superuser (ตรงกับ THREAT_MODEL "นอกขอบเขต")
  จึงต้องมีการเข้ารหัสเนื้อหารายคอลัมน์ (BRIEF 5.9 ข้อ 3) เป็นชั้นที่สอง

**ที่ spike นี้ไม่ได้พิสูจน์:** การเข้ารหัสรายคอลัมน์, ต้นทุน RAM/CPU ของ PostgreSQL บน Pi 5, backup ด้วย BYPASSRLS

## การตัดสิน

**ไม่ใช้ฐานข้อมูลในรุ่นนี้ · ข้อมูลของแต่ละคนเป็นไฟล์ใน home ของคนนั้น (0700) เขียนแบบ atomic** · ใช้ทีละคน ไม่มีข้อมูลที่แชร์ข้ามผู้ใช้ · OS แยกข้อมูลให้ด้วยสิทธิ์ไฟล์ · PostgreSQL กิน RAM ตลอดเวลาและต้องมี migration/backup เพิ่ม · ผล spike บน Pi 4 (13/13) เก็บไว้เป็นทางเลือกที่ประเมินแล้วในเล่ม ไม่ยืนยันซ้ำบน Pi 5 · [ข้อเสนอรอบ 3](../reviews/2026-09-28-scope-cut.md)
