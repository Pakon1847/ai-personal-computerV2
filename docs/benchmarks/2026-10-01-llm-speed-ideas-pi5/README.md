Gemma 4 E2B Q4_K_M · llama.cpp 86ea01d · `-c 4096 -np 1 -t 3 -fa off -cram 512` · Pi 5 8GB (ตอนวัดมี AI ของ pakon1 อีกตัวทำงานอยู่ด้วย)

## 1. Speculative decoding แบบ n-gram (ไม่ต้องมีโมเดลร่าง) · **ไม่ช่วย**

- อ้างอิง: Leviathan, Kalman, Matias. *Fast Inference from Transformers via Speculative Decoding*. ICML 2023 (arXiv:2211.17192)
  — เดาหลาย token ล่วงหน้าแล้วให้โมเดลหลักตรวจรวดเดียว ผลลัพธ์เหมือนเดิมทุกตัวอักษรเมื่อ greedy
- ชุด: ชุดสอบจบ E01–E12 + A01–A05 · temperature 0 · เกณฑ์ (ประกาศก่อน): เร็วขึ้น ≥ 1.2 เท่า · คำตอบเหมือนเดิม ≥ 16/17
- ผล: ปกติ **6.40** token/วิ · `--spec-type ngram-simple` **6.67** (1.04 เท่า · อยู่ในช่วงแกว่งของเครื่อง) · คำตอบเหมือนเดิม 17/17 ·
  log มีการเดาเกิดขึ้นแค่ 1 คำขอ (ยอมรับ 4/24) → ประโยคคำตอบไม่ค่อยซ้ำคำถาม n-gram จึงหาอะไรมาเดาไม่ได้
- ทางโมเดลร่าง: ต้องใช้ tokenizer เดียวกัน · ในเครื่องไม่มีโมเดล Gemma 4 ที่เล็กกว่า E2B → ไม่ได้ลอง
- ไฟล์: `docs/benchmarks/2026-10-01-spec-pi5/{none,ngram-simple}.json` · ตัววัด `python -m aipc.spikes.spec_bench`

## 2. เก็บแคช prompt (system + รายการสกิล) ลงดิสก์ แล้วโหลดคืนตอน AI เริ่มใหม่ · **ช่วยมาก**

ปัญหาที่วัดได้: หลัง login / AI เริ่มใหม่ ต้องอ่าน prompt 1,181 token ก่อนตอบข้อความแรก = **52.8 วิ** (22 token/วิ) ·
แอปอุ่นแคชให้แล้ว แต่ผู้ใช้ที่พิมพ์เร็วกว่า 1 นาทีหลัง login ยังรอ

| ขั้น | ผล |
|---|---|
| อ่าน prompt ครั้งแรก (ไม่มีแคช) | 52.7 วิ |
| บันทึกแคชของ slot (`POST /slots/0?action=save`) | 8 ms · ไฟล์ 13.6 MB |
| เริ่ม AI ใหม่ แล้วโหลดคืน (`action=restore`) · **ไม่มี** `--swa-full` | โหลด 7 ms แต่คำถามถัดไป **ยังอ่านใหม่ทั้งหมด 52.7 วิ** (cache_n = 0) |
| เหมือนกัน · **มี** `--swa-full` | โหลด 7 ms · คำถามแรก **0.66 วิ** (อ่านเพิ่ม 13 token · cache_n 1,175) |
| RAM ที่เพิ่มเพราะ `--swa-full` | RssAnon 1,478.8 → 1,534.0 MB (**+55 MB**) |

- ทำไมต้อง `--swa-full`: Gemma ใช้ sliding-window attention · แคชแบบย่อ (ค่าเริ่มต้น) ใช้ส่วนต้นซ้ำหลังโหลดคืนไม่ได้
  (llama.cpp เตือน "using full-size SWA cache" · ref ggml-org/llama.cpp PR 13194)
- ภายในโปรเซสเดียวกัน (ไม่เริ่มใหม่) แคชใช้ซ้ำได้ตามปกติ: คำถามถัดไปอ่านเพิ่ม 14 token 0.8 วิ → การอุ่นแคชของแอปทำงานถูกแล้ว
- `--no-slots` (ที่แอปใช้ปิดหน้าดูสถานะ) **ยังบันทึก/โหลดได้** · ชื่อไฟล์แบบ `../../etc/passwd` ถูกปฏิเสธ ("Invalid filename")
- ความเป็นส่วนตัว: บันทึกหลังอุ่นทันที = มีแค่ system prompt + รายการสกิล + "สวัสดี" (ไม่มีข้อความของผู้ใช้) · เก็บใน home ของผู้ใช้
- **ข้อเสนอ:** การ์ด 0018 (ร่าง) · ใช้กับ AI ในแอป: `--swa-full --slot-save-path ~/.cache/aipc/llm-slots` + อุ่นครั้งแรกแล้วบันทึก ·
  ครั้งต่อไปโหลดคืนก่อน (ชื่อไฟล์ = hash ของโมเดล + system prompt + รายการเครื่องมือ · ไม่ตรง = อุ่นใหม่)

## 3. ขนาด prompt โตตามจำนวนสกิล (ผลต่อการ์ด 0017) · **ปัญหาจริง ต้องวางแผน**

| รายการเครื่องมือ | token ของรายการ | prompt ทั้งหมด | อ่านครั้งแรก |
|---|---|---|---|
| สกิลในตัว 6 + ask-cloud + create-skill | 778 | 1,166 | 52.8 วิ |
| + สกิลที่ Claude สร้าง 5 ตัว | 1,316 | 1,634 | 74.0 วิ |

- สกิล 1 ตัว ≈ **+94 token** ≈ +4.3 วิ ตอนไม่มีแคช · ประมาณ **~30 สกิล prompt จะเกิน 4,096 token (ขนาดบริบท)** → สกิลอัตโนมัติชนเพดาน
- แนวทางจากงานวิจัย (ตรวจที่ arXiv แล้ว):
  - Gan, Sun. *RAG-MCP: Mitigating Prompt Bloat in LLM Tool Selection via Retrieval-Augmented Generation*. 2025 (arXiv:2505.03275)
    — ค้นเฉพาะเครื่องมือที่เกี่ยวข้องก่อนส่งให้โมเดล · prompt ลดกว่า 50% · เลือกเครื่องมือถูก 43.13% เทียบ 13.62%
  - Moon et al. *Efficient and Scalable Estimation of Tool Representations in Vector Space*. 2024 (arXiv:2409.02141)
    — Tool2Vec: แทนเครื่องมือด้วยเวกเตอร์จาก "ตัวอย่างคำขอ" แทนคำอธิบาย · Recall@K ดีขึ้นสูงสุด 27–30 จุด
- **ข้อเสนอ:** ส่งเฉพาะสกิล top-k (เช่น 5) ที่ใกล้กับข้อความ + สกิลในตัว · ใช้ตัวอย่างคำขอของสกิล (สกิลของเรามีครบทุกตัว) ·
  ต้องวัดก่อนใช้: ชุดเลือกสกิล 58 ข้อ + ชุดสำนวนอื่น ต้องไม่ลดลง · เวลาเลือกบน Pi ≤ 0.2 วิ · ยังไม่ได้ทำ
