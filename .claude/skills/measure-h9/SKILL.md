# วัดผลตาม H9

หลัก: **ตัวเลขในเล่มต้องเชื่อถือได้แม้ผลออกมาไม่สวย** · ทำตามลำดับ ห้ามข้ามขั้น 1–3 · กติกาเต็มอยู่ใน `CLAUDE.md` หัวข้อ "ระดับหลักฐาน" และ `docs/TESTING.md`

## 1. ก่อนสร้าง/ก่อนวัด: เกณฑ์

- อ่านเกณฑ์ในการ์ด `docs/design/NNNN-*.md` · ไม่มี → ร่างเกณฑ์ (ตัวเลขชัด วัดได้) แล้ว **รอ Pakon อนุมัติ**
- เกณฑ์ต้องแยก "ทำผิด" (อันตราย) ออกจาก "ไม่ทำ" (ปลอดภัย) และมีเกณฑ์ "ไม่แย่กว่าของเดิม"

## 2. ชุดข้อมูล: ชุดพัฒนา ≠ ชุดทดสอบ

- **ชุดพัฒนา** ใช้ปรับได้ (prompt · กฎ · ค่าตั้ง)
- **ชุดทดสอบ (held-out)** ห้ามใช้ปรับ · ต้องเขียน **ก่อนเห็นผลของระบบ** · ดีที่สุดคือคนอื่นเขียน (Pakon หรือ subagent ที่สั่งว่า
  ห้ามเปิดโค้ด/ชุดเดิม/ผลเดิม และห้ามยกตัวอย่างประโยคมาในรายงาน) · ผู้วัดไม่เปิดอ่านจนรันเสร็จ
- บทเรียนจริง: ชุดพัฒนาที่ผู้พัฒนาเขียนเองได้ 91% แต่ชุดอิสระได้ 49% ([ผล](../../../docs/benchmarks/2026-10-14-voice-round2/README.md))
- ห้ามแก้ไฟล์ใน `tests/data/` เพื่อให้ผ่าน

## 3. ประกาศก่อนรัน (commit = หลักฐานว่าตั้งก่อนเห็นผล)

สร้าง `docs/benchmarks/<YYYY-MM-DD>-<เรื่อง>/README.md` แล้ว commit **พร้อมชุดทดสอบ** ก่อนรัน:

```markdown
# <เรื่อง> · **สถานะ: ประกาศก่อนรัน** (<วันที่> · ผลจะเติมด้านล่างโดยไม่แก้ส่วนนี้)
## คำถาม/ทำไมต้องวัด
## ชุดทดสอบ (path · commit · ใครเขียน · เขียนเมื่อไร)
## สิ่งที่วัด (ตัวไหน · ค่าตั้ง · เครื่อง)
## วิธีนับ (ตาราง: ok / ทำผิด / ไม่ทำ / ไม่ใช่เป้าหมายแต่ทำ — นิยามชัดก่อนรัน)
## เกณฑ์ (ลอกจากการ์ด)
## ทำซ้ำ (คำสั่งเต็ม)
## ผล (ยังไม่รัน)
```

## 4. รัน

- **ชุดทดสอบรันครั้งเดียว** ต่อรุ่น · เห็นจุดแก้จากชุดทดสอบ → **ห้ามแก้แล้วรันชุดเดิมซ้ำเพื่ออ้างผลดีขึ้น** · ชุดนั้นกลายเป็นชุดพัฒนา ต้องมีชุดทดสอบใหม่
- ตัวเลข **ความเร็ว/RAM มาจาก Pi 5 เท่านั้น** · Pi 4 = ความถูกต้องบน ARM (เขียน "(Pi 4)") · โน้ตบุ๊ก = คัดกรองความแม่นได้ เวลาใช้ไม่ได้
- ก่อนวัดบน Pi: `aipc.doctor` · รอ < 65°C ก่อนแต่ละรอบ · จด `vcgencmd get_throttled` ก่อน/หลัง (ไม่ใช่ `0x0` = เวลาเป็นเวลาตอนเครื่องร้อน)
- งานนานบน Pi ดู skill `pi-deploy` หัวข้อ 4 (KillUserProcesses)

## 5. บันทึกผล (ส่วน "ผล" ของ README เดิม)

- วันเวลา · commit · ฮาร์ดแวร์ · บัญชีที่รัน · อุณหภูมิ/throttle · ไฟล์ค่าดิบ (`*.json` `*.log`) commit คู่กัน
- ตารางเทียบเกณฑ์ทีละข้อ ✅/❌ · **ไม่ผ่าน = เขียนว่าไม่ผ่าน** · แยกสาเหตุของข้อที่พลาด
- "0 จาก N" ≠ ความเสี่ยง 0% (ขอบบน 95% ≈ 3/N) · ไม่ใช้คำว่า "พร้อม 100%"
- ห้าม commit เสียง/ภาพของคน ความลับ หรือโมเดล

## 6. หลังวัด

- อัปเดตการ์ด (หัวข้อผล) และ `docs/STATUS.md` · ระดับหลักฐานตาม CLAUDE.md (ผลไม่ผ่านเกณฑ์ ≠ ระดับ 4)
- ไม่ผ่าน → ตามการ์ด = **ไม่ติดตั้ง** จนกว่า Pakon ตัดสิน · เสนอทางเลือกพร้อมข้อดีข้อเสีย แล้วฟันธง 1 ทาง
- รายงานตาม "รายงานเมื่อจบงาน" ใน CLAUDE.md พร้อม "ถ้ากรรมการถามจะตอบว่าอะไร"
